# 03 — Elevation Roadmap

What a senior engineer would invest in if they had 3–6 more months on this project. Each area names the **current state** with file references, the **senior-engineer target**, **alternatives** with tradeoffs, and **knowledge prerequisites** so a learner can actually pursue the upgrade.

## Executive view

In priority order — the highest-leverage upgrades for this specific repo:

1. **Test depth.** The test plumbing exists (`tests/helper.py`, `vendor/pytest_cov_helper.py`, `mise run cov`) but there are zero actual test files. Adding even smoke-tests against each example script would be the highest-ROI change and unlocks every other elevation.
2. **CI / GitHub Actions.** No `.github/workflows/` exists. Without CI, regressions ship silently and the test infra above never runs on PR. Codecov and ReadTheDocs setup tasks are scaffolded in `mise.toml` but the workflow YAML is missing.
3. **Type checking + lint.** No `mypy` / `ruff` / `pre-commit` config. The codebase is small enough that adding type hints + a baseline ruff config is a one-day task; the gain compounds for every new file.
4. **Production safety for the merge / vacuum scripts.** `AWS_S3_ALLOW_UNSAFE_RENAME="true"` and `vacuum(retention_hours=0, enforce_retention_duration=False)` are demo-only patterns. A senior version would surface the "demo vs production" distinction loudly and offer a side-by-side multi-writer configuration with DynamoDB locking.
5. **Observability.** Bare `print()` statements throughout examples. A senior version would use structured logging with timing/row-count metrics so a learner can compare the cost of `merge` vs `overwrite` empirically.
6. **A second curriculum thread on streaming / incremental architecture.** The 16-script linear curriculum stops at "Bronze→Silver one-shot". Real production also needs Kinesis/Kafka → micro-batch → CDC patterns. This is the obvious "next book" the project hints at without delivering.

## Upgrade areas

### A. Test depth and coverage

- **Current state:** `delta_lake_and_polars_basic/tests/` contains only `__init__.py` and `helper.py`. `tests/` at the repo root: no actual test files. `mise run test` and `mise run cov` pass vacuously. The 16 example scripts are entirely untested — a regression in `polars` or `deltalake` would only be caught when someone runs the scripts by hand.
- **Senior target:** A `tests/test_examples.py` (or per-module `tests/test_examples_NN.py`) that subprocess-runs each script and asserts (a) exit code 0, (b) one expected ASCII marker per script in stdout, (c) the expected S3 artifact exists at the end (use a moto-mocked S3 in CI). Coverage threshold ≥ 70% on the `one/` package.
- **Alternatives:**
  1. **Subprocess each script + check exit code only.** Cheap, fast, catches all hard failures. Misses semantic regressions (e.g., merge wrote the wrong rows).
  2. **Refactor each script's body into a `main()` function and call it from a test.** Better coverage, but means modifying every example — could obscure the linear-script teaching value. Tradeoff: pedagogy vs. testability.
  3. **Snapshot tests on the final S3 state per script.** Use moto, write to `s3://mocked-bucket/...`, then diff a snapshot file. Catches semantic regressions, but slow and brittle (file ordering, timestamps).
  - **Recommendation:** Start with #1 (cheap, catches the most common breakage), evolve to #2 only if regressions slip through.
- **Knowledge prereqs:**
  - `pytest`'s `subprocess.run` integration and `capsys` / `caplog`.
  - `moto` (AWS mock library) — specifically `mock_s3` decorator and DynamoDB mocking if you go multi-writer.
  - The project's existing `vendor/pytest_cov_helper.py` pattern (subprocess-launched pytest with per-module coverage).
- **Learning path:**
  1. Skim the `vendor/pytest_cov_helper.py` source and the `tests/helper.py` wrapper — understand why this project chose subprocess pytest.
  2. Read the `moto` docs section on mocking S3 (the "decorators" page).
  3. Read pytest's own docs on `tmp_path` and `monkeypatch`.
  4. Build `tests/test_examples_02.py` first (the polars-etl scripts don't need moto), then extend to S3-touching scripts.

### B. CI / GitHub Actions

- **Current state:** No `.github/workflows/` directory. `mise.toml` has `setup-codecov` and `setup-readthedocs` tasks scaffolded but they reference `.mise/tasks/setup-codecov.py` files that aren't in the repo. CLAUDE.md mentions `.github/workflows/main.yml` but the file does not exist (drift).
- **Senior target:** A `.github/workflows/main.yml` that on every push/PR runs `mise install && mise run inst && mise run cov && mise run build-doc`, uploads coverage to Codecov, and on tag push runs `mise run build && mise run publish` (with `PYPI_TOKEN` from secrets).
- **Alternatives:**
  1. **GitHub Actions with `mise-action`** — clean, mirrors local dev.
  2. **`uv` directly + cache** — skip mise, simpler workflow file; loses the "single source of truth" property.
  3. **`tox` matrix across Python 3.12 / 3.13 / 3.14** — useful if you actually plan to support multiple Pythons; overkill for this project given `requires-python >= 3.12`.
  - **Recommendation:** #1 — it mirrors the local dev flow, and the project's whole point is "mise is the source of truth".
- **Knowledge prereqs:**
  - GitHub Actions workflow YAML syntax, `actions/checkout@v4`, `mise-action`, `actions/cache@v4`.
  - Codecov upload action and how `codecov.yml` thresholds work.
  - Secrets handling (`secrets.PYPI_TOKEN`, `secrets.CODECOV_TOKEN`).
- **Learning path:**
  1. Read the official GitHub Actions "Quickstart for Python" then the `mise-action` README.
  2. Look at a working workflow in any well-maintained `uv`-based project (e.g., `astral-sh/ruff` is a benchmark — though larger).
  3. Write a minimal `main.yml` that does only `mise install && mise run cov`, get it green, then layer on docs build + publish.

### C. Type checking + lint

- **Current state:** Source files are mostly type-hint-free (only the mixins use `typing.TYPE_CHECKING` blocks for the boto3 types). No `mypy.ini`, no `pyproject.toml [tool.mypy]`, no `ruff` config, no `pre-commit`. `boto3-stubs[s3]` is a dependency, which is wasted without mypy/pyright to consume the stubs.
- **Senior target:** Add `[tool.ruff]` + `[tool.mypy]` to `pyproject.toml`, fix the (small) number of failures, add a `pre-commit` config running both. Add `mise run lint` and `mise run typecheck` tasks, wire into CI.
- **Alternatives:**
  1. **ruff + mypy** — industry standard for new Python projects.
  2. **ruff + pyright** — pyright is faster and has better inference; mypy has wider plugin ecosystem (`pandas-stubs`, etc.). For this codebase pyright is probably a better fit.
  3. **Just `ruff`** — covers ~80% of the lint/format value at 5% of the setup cost. Skip type checking until the codebase grows.
  - **Recommendation:** #1 for the conventional path, #3 if you want minimum-friction.
- **Knowledge prereqs:**
  - `ruff` rule selectors (`E`, `F`, `I`, `B`, `UP`, etc.) and `pyproject.toml [tool.ruff]` config.
  - `mypy` configuration (`strict_optional`, `disallow_untyped_defs`, per-module overrides).
  - The boto3-stubs ecosystem.
- **Learning path:**
  1. Run `ruff check .` once with default config, see what fires.
  2. Read the `ruff` rules page; pick a starting rule set (`E`, `F`, `I`, `B`, `UP`, `SIM`).
  3. Add `mypy --strict` and watch what fails on `one/one_03_boto_ses.py` — that's where the boto3 types live.

### D. Production safety for merge / vacuum (the "demo vs prod" distinction)

- **Current state:** `one/one_03_boto_ses.py` sets `AWS_S3_ALLOW_UNSAFE_RENAME="true"` in `polars_storage_options`. `examples/05-vacuum-schema/s01_vacuum.py` calls `vacuum(retention_hours=0, enforce_retention_duration=False)`. Both are explicit demo-only patterns; a careless learner might copy-paste these settings into production and corrupt a multi-writer table.
- **Senior target:** Refactor `polars_storage_options` into two flavors — `one.polars_storage_options_demo` (current behavior) and `one.polars_storage_options_prod` (no unsafe rename, requires DynamoDB lock table). Add a `s03_vacuum_prod_safe.py` example that uses the default 168-hour retention with a comment block explaining why. Update READMEs to flag the distinction.
- **Alternatives:**
  1. **Two flavors of storage options** (above).
  2. **Refuse to construct `one` without an explicit `mode=` argument** ("demo" or "prod"). Forces the learner to decide; can't accidentally inherit demo defaults.
  3. **Document only, no code change.** Cheaper, but learners who skim won't catch it.
  - **Recommendation:** #2 — making the decision *required* is the only real safety.
- **Knowledge prereqs:**
  - Delta Lake's S3 + DynamoDB lock pattern (the "S3 commit coordinator" docs from Databricks / deltalake).
  - Why optimistic concurrency requires a barrier for non-atomic stores like S3.
  - The `vacuum` retention math — why "remove files older than X hours" needs to be > "longest in-flight query".
- **Learning path:**
  1. Read the deltalake-rs docs section on "Concurrent writes to a Delta table".
  2. Read the Delta Lake spec § "Atomicity, Consistency, and Isolation".
  3. Set up a DynamoDB lock table in a sandbox account; modify `one_03_boto_ses.py` to point at it; re-run module 03 with two parallel processes and observe the lock acquisition.

### E. Observability (structured logging + timing)

- **Current state:** Every example uses bare `print(df)` or `print("Wrote N rows")`. No timing, no row counts in a parseable format, no log levels. Learners can't compare "merge vs overwrite" empirically.
- **Senior target:** Add `loguru` (or `structlog`) to `[project.optional-dependencies.dev]`. Wrap each script's top-level work in a context manager that prints structured records `{op: "write_delta", mode: "overwrite", n_rows: 1000, duration_ms: 312}`. Update one or two examples to use it as a reference pattern.
- **Alternatives:**
  1. **`loguru`** — zero-config, great default output, async-safe.
  2. **`structlog`** — more configurable; better for production pipelines that need to ship to ELK/Datadog.
  3. **Standard library `logging`** — no extra dep but more config overhead.
  - **Recommendation:** `loguru` for the learning-repo persona; if this graduated to production, switch to `structlog`.
- **Knowledge prereqs:**
  - Differences between standard `logging`, `loguru`, `structlog`.
  - JSON log output vs human-readable, and when each matters.
  - Context propagation (request_id, transaction_id) — relevant once you go multi-script.
- **Learning path:**
  1. Read the `loguru` README — should take 10 minutes.
  2. Read one chapter of "Building Event-Driven Microservices" (Adam Bellemare) on structured logging.
  3. Pick one example (`06-full-etl/s03_incremental.py`), instrument it, and compare the dev experience.

### F. A second curriculum thread — streaming / CDC

- **Current state:** The 16-script curriculum stops at "Bronze→Silver, one-shot batch". The closest streaming hint is `s03_incremental.py` which re-runs the whole ETL on every new batch.
- **Senior target:** A new `07-streaming/` module with 3–4 scripts: (a) Kinesis Data Streams → micro-batch with `deltalake`'s `write_delta` in append mode, (b) Bronze→Silver as a stream consumer, (c) CDC via Debezium → upsert into Delta, (d) backfill replay against time-traveled state.
- **Alternatives:**
  1. **Add a streaming module.** Best fit for the project's "fintech production reality" framing.
  2. **Add an `07-iceberg-vs-delta/` comparative module.** Educational but pulls the project away from its current depth in one technology.
  3. **Add an `07-mlops/` module** (feature store on Delta). Different audience.
  - **Recommendation:** #1 — closest to the original project context.
- **Knowledge prereqs:**
  - Kinesis Data Streams basics, KCL vs polling, partition keys.
  - Debezium / change data capture concepts.
  - Idempotency and exactly-once semantics in micro-batch.
  - Delta Lake's `CDF` (Change Data Feed) feature.
- **Learning path:** Substantial — this is probably a 2–4 week side project. Start with Confluent's "Apache Kafka 101" series, then the Debezium PostgreSQL tutorial, then the deltalake-rs CDC API docs.

### G. Developer experience polish

- **Current state:** No `pre-commit`, no `.envrc` for direnv users, no `.editorconfig`, no shell completions exported from `mise`. Setup is "read the README, run a few commands" — works but requires effort.
- **Senior target:** Add `.pre-commit-config.yaml` (ruff + mypy), `.editorconfig`, a short "GETTING_STARTED.md" with the 60-second path, and a Makefile-style alias layer if `mise run` feels heavy.
- **Alternatives:**
  1. **pre-commit + editorconfig only** — minimum useful.
  2. **DevContainer / `.devcontainer/devcontainer.json`** — gives one-click VSCode setup; useful for workshop-style learning.
  3. **Nix flake** — overkill unless the audience is into reproducible builds.
  - **Recommendation:** #1, with #2 as a bonus if you'll teach this in workshops.
