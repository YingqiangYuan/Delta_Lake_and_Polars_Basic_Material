# 03 — Elevation Roadmap

## Scope notes

This project is a learning/POC repo, not a production service. Elevation items focus on: (a) project improvements that would make it production-grade, and (b) knowledge/skills the owner would gain by doing each upgrade.

## Executive view

1. **Real test suite with CI** — Replace implicit "run the script and check stdout" with pytest assertions and GitHub Actions gating.
2. **Change data capture (CDC) instead of full recompute** — The Silver ETL re-reads all of Bronze every run. A CDC approach would process only new/changed rows.
3. **Observability and data quality checks** — No validation, no metrics, no alerting on bad data.
4. **Multi-writer safety and concurrency** — `AWS_S3_ALLOW_UNSAFE_RENAME=true` skips locking. Production multi-writer needs DynamoDB or S3 conditional writes.
5. **Schema registry and contract testing** — Schema evolution in `05-vacuum-schema` is ad-hoc. A schema registry would enforce contracts between Bronze and Silver.

## Upgrade areas

### 1. Test depth and coverage

**Current state:**
- `tests/` directory has helper infrastructure but no test files (`delta_lake_and_polars_basic/vendor/pytest_cov_helper.py`).
- Example scripts are self-verifying via `print()` and some `assert` statements (e.g., `examples/03-merge-upsert/s02_credit_profile.py`).
- `mise run cov` runs but covers only the core package, not the examples.
- GitHub Actions workflow exists (`.github/workflows/main.yml`) but scope is unclear.

**Senior-engineer target state:**
- Each example module has a corresponding `tests/test_<module>.py` file.
- Tests use mocked S3 (e.g., `moto` library) or a local MinIO instance so they run without AWS credentials.
- CI runs all tests on every PR. Coverage gate at 80%+.
- Integration tests (against real S3) run nightly or on-demand.

**Alternatives considered or worth considering:**
- **moto (mock AWS):** Zero-infra testing, but behavior may diverge from real S3 for edge cases (Delta log atomicity). Tradeoff: fast + free vs. fidelity risk.
- **MinIO (local S3-compatible):** High fidelity, but requires Docker and setup. Tradeoff: realistic vs. operational overhead for a POC.
- **LocalStack:** Full AWS emulation but heavy. Overkill for S3-only use.

**Knowledge prerequisites:**
- pytest fixtures and parameterization
- moto library for mocking boto3 services
- GitHub Actions workflow authoring (matrix builds, secrets)
- Code coverage tooling (`pytest-cov`, codecov.io)

**Suggested learning path:**
1. pytest official tutorial (fixtures, parametrize)
2. moto library docs — S3 mock usage
3. GitHub Actions docs — "Building and testing Python"
4. Real Python — "Python Testing with pytest" (book)

### 2. Change data capture (CDC)

**Current state:**
- `examples/06-full-etl/s03_incremental.py` re-reads ALL of Bronze, re-applies the full ETL pipeline, then merges into Silver.
- This works for small datasets but scales O(total_rows) instead of O(new_rows).
- No mechanism to track which Bronze rows have already been processed.

**Senior-engineer target state:**
- Track a high-water mark (e.g., latest `version` or `etl_ts`) in Silver metadata.
- On each incremental run, read only Bronze rows newer than the high-water mark.
- Apply ETL only to the new rows, then merge just those into Silver.
- Result: O(new_rows) processing.

**Alternatives considered or worth considering:**
- **Delta Lake CDF (Change Data Feed):** Delta's built-in mechanism for tracking row-level changes between versions. Enable with `delta.enableChangeDataFeed`. Tradeoff: elegant but requires deltalake library support (available in delta-rs 0.17+).
- **Watermark in a separate metadata table:** Store `{last_processed_version, timestamp}` in a small Delta or JSON file. Tradeoff: simple, portable, but extra bookkeeping.
- **Event-driven (S3 notifications → Lambda):** Trigger ETL on new file arrival. Tradeoff: production-grade but adds AWS infra complexity.

**Knowledge prerequisites:**
- Delta Lake Change Data Feed (CDF) specification
- Watermark/checkpoint patterns in batch ETL
- Idempotent processing (handling reprocessing without duplicates)

**Suggested learning path:**
1. Delta Lake docs — "Change Data Feed" chapter
2. "Designing Data-Intensive Applications" by Martin Kleppmann — Chapter 11 (Stream Processing, but the batch CDC parallels apply)
3. delta-rs GitHub — look at CDF support status in the Python binding

### 3. Observability and data quality

**Current state:**
- No data validation (no checks for nulls, schema conformance, value ranges).
- No metrics (row counts, processing time, error rates) beyond `print()`.
- No alerting or monitoring.
- The only "observability" is reading stdout after manual runs.

**Senior-engineer target state:**
- Data quality checks on each ETL step: null checks, uniqueness constraints, value range assertions, schema validation.
- Metrics emitted to CloudWatch or a local log: rows_in, rows_out, rows_rejected, processing_time_ms.
- Alerting on quality failures (e.g., >5% rows rejected → SNS notification).

**Alternatives considered or worth considering:**
- **Great Expectations (GX):** Full data quality framework with expectation suites, profiling, and docs. Tradeoff: powerful but heavy for a POC.
- **Pandera:** Lightweight DataFrame validation (supports Polars). Tradeoff: simpler than GX, Polars-native, but less ecosystem.
- **Custom assertions:** What the project already does minimally. Tradeoff: zero dependency but no reuse, no reporting.

**Knowledge prerequisites:**
- Data quality dimensions (completeness, accuracy, consistency, timeliness)
- Pandera library (Polars integration)
- CloudWatch custom metrics API
- Structured logging in Python (`structlog` or `logging` with JSON formatter)

**Suggested learning path:**
1. Pandera docs — Polars integration guide
2. "Fundamentals of Data Engineering" by Joe Reis & Matt Housley — Chapter 8 (Data Quality)
3. AWS CloudWatch custom metrics tutorial
4. structlog library docs

### 4. Multi-writer safety and concurrency

**Current state:**
- `polars_storage_options` includes `AWS_S3_ALLOW_UNSAFE_RENAME=true` (see `delta_lake_and_polars_basic/one/one_03_boto_ses.py`).
- This skips the DynamoDB-based locking that Delta Lake uses for atomic commits on S3.
- Fine for single-writer POC scripts. Dangerous when multiple processes write to the same Delta table.

**Senior-engineer target state:**
- Use DynamoDB-based locking (`delta-rs` supports this via `AWS_S3_LOCKING_PROVIDER=dynamodb`).
- Or use S3 conditional writes (available since S3 added `If-None-Match` support in 2024).
- Concurrent ETL processes can safely merge into the same Silver table.

**Alternatives considered or worth considering:**
- **DynamoDB lock table:** The standard Delta Lake on S3 approach. Tradeoff: proven, but adds a DynamoDB table + IAM permissions.
- **S3 conditional writes (If-None-Match):** Newer S3 feature that enables atomic puts without DynamoDB. Tradeoff: simpler infra, but delta-rs support may be experimental.
- **Single-writer architecture:** Design the system so only one writer ever touches a table. Tradeoff: simple, but limits concurrency and requires orchestration.

**Knowledge prerequisites:**
- Delta Lake transaction log protocol (how commits work on S3)
- DynamoDB provisioning and IAM configuration
- Optimistic concurrency control concepts
- S3 consistency model (read-after-write, conditional writes)

**Suggested learning path:**
1. Delta Lake protocol spec — "Storage Configuration" section
2. delta-rs docs — "S3 Options" (locking providers)
3. AWS blog — "S3 conditional writes" (2024 announcement)
4. "Designing Data-Intensive Applications" — Chapter 7 (Transactions)

### 5. Schema registry and contract testing

**Current state:**
- `examples/05-vacuum-schema/s02_schema_evolution.py` demonstrates ad-hoc schema evolution with `schema_mode="merge"`.
- No explicit schema contract between Bronze and Silver layers.
- If Bronze schema changes unexpectedly, Silver ETL might silently produce wrong results.

**Senior-engineer target state:**
- Schema definitions stored in a registry (e.g., a `schemas/` directory with JSON/Avro schema files, or a proper schema registry service).
- Bronze write validates incoming data against the registered schema.
- Silver ETL validates its input matches the expected Bronze schema.
- Schema changes require explicit migration (versioned schema evolution).

**Alternatives considered or worth considering:**
- **File-based schemas (`schemas/*.json`):** Simple, version-controlled. Tradeoff: no runtime enforcement, manual.
- **Pandera schemas in code:** Define schemas as Python classes. Tradeoff: code-level enforcement, testable, but coupled to Python.
- **AWS Glue Schema Registry:** Managed service. Tradeoff: full-featured, but adds AWS dependency and cost.

**Knowledge prerequisites:**
- Schema evolution strategies (backward/forward/full compatibility)
- Avro or JSON Schema specification
- Pandera schema definition for Polars DataFrames
- Contract testing concepts

**Suggested learning path:**
1. Confluent docs — "Schema Evolution and Compatibility"
2. Pandera docs — Polars DataFrameSchema
3. "Fundamentals of Data Engineering" — Chapter 5 (Data Storage, schema management)

### 6. Deployment maturity (CI/CD)

**Current state:**
- `.github/workflows/main.yml` exists but the pipeline is minimal.
- `mise run publish` pushes to PyPI manually.
- No automated release pipeline, no staging environment, no rollback.
- Scripts are run manually from a developer's machine.

**Senior-engineer target state:**
- CI: lint + type-check + test on every PR.
- CD: automated package publish on tag push.
- For the ETL pipeline: orchestrated via Airflow, Dagster, or Step Functions with retry/alerting.
- Infrastructure-as-code for the S3 bucket, IAM roles, and (if added) DynamoDB lock table.

**Alternatives considered or worth considering:**
- **Dagster:** Modern data orchestrator with asset-based paradigm. Tradeoff: elegant for data pipelines, but learning curve.
- **Airflow:** Industry standard. Tradeoff: mature ecosystem, but heavy for a small pipeline.
- **AWS Step Functions:** Serverless orchestration. Tradeoff: low-ops, but vendor lock-in and JSON-based workflow definition.

**Knowledge prerequisites:**
- GitHub Actions advanced features (matrix, reusable workflows, environments)
- Data pipeline orchestration concepts (DAGs, retry, idempotency)
- Infrastructure-as-code (Terraform or AWS CDK)

**Suggested learning path:**
1. GitHub Actions docs — "Reusable workflows"
2. Dagster tutorial — "Software-Defined Assets"
3. Terraform AWS provider tutorial

### 7. Developer experience

**Current state:**
- `mise.toml` provides good task definitions.
- No linter, no type checker, no formatter configured.
- No pre-commit hooks.

**Senior-engineer target state:**
- `ruff` for linting + formatting (fast, Rust-based, replaces flake8+black+isort).
- `mypy` or `pyright` for type checking.
- Pre-commit hooks running ruff + mypy on staged files.
- `mise run lint` and `mise run format` tasks.

**Alternatives considered or worth considering:**
- **ruff:** All-in-one linter + formatter. Fast. Tradeoff: newer, but rapidly becoming standard.
- **black + flake8 + isort:** Established stack. Tradeoff: more mature, but slower and more config.

**Knowledge prerequisites:**
- Python linting and formatting conventions (PEP 8, PEP 257)
- ruff configuration (`pyproject.toml` `[tool.ruff]` section)
- pre-commit framework
- Type annotation in Python (typing module, generics, Protocol)

**Suggested learning path:**
1. ruff docs — getting started
2. mypy docs — "Getting started"
3. pre-commit.com — hook configuration

## Projects-not-included

- **Gold layer:** The pipeline stops at Silver. A Gold layer (aggregated/business-specific tables) is the natural next step but was not implemented. Evidence: no `07-gold-*` directory.
- **Partitioning:** Delta tables are written without partitioning (`partition_by` parameter). For large tables, partitioning by date or category improves read performance. Evidence: no `partition_by=` in any `write_delta` call.
- **Z-ordering / optimize:** Delta Lake supports file compaction and Z-ordering for query optimization. Not demonstrated. Evidence: no `DeltaTable.optimize()` calls anywhere.
- **Streaming ingestion:** All scripts are batch. A streaming variant (e.g., Polars streaming mode or Kafka → Delta) was not explored. Evidence: no streaming-related imports or scripts.
