# 04 — Quiz Bank

## How these questions are designed

These items are **discussion prompts**, not fill-in-the-blank trivia. Each question opens up a topic; each expected answer is **3–5 sentences** that names file paths AND explains the underlying principle (知其然知其所以然 — know-what AND know-why). When grading:

1. Questions are discussion prompts, not fill-in-the-blank.
2. A good answer is 3–5 sentences that names file paths AND explains the principle.
3. If a question can be answered in one sentence, the question was too narrow.

### What good vs bad questions look like

- ❌ Bad: "Which command installs the dependencies?" → forces recital of `mise run inst`. Pure memorization.
- ✅ Good: "A new contributor asks how to get a working environment — where do you point them and what would you tell them about how `mise`, `uv`, and `.env` fit together?" → forces opening `mise.toml`, explaining the layering, and surfacing the AWS profile dependency.

- ❌ Bad: "What is the `one` singleton?" → one-line definition.
- ✅ Good: "Walk through what the `one` singleton actually owns and why the codebase routes all AWS access through it instead of letting each script create its own boto3 session." → forces a tour of the mixin files, with the consolidation rationale.

- ❌ Bad: "Does `mode='append'` deduplicate?" → recall.
- ✅ Good: "Why do `s02_append.py` and the merge examples coexist in the curriculum? Walk through what append does, what it deliberately *doesn't* do, and the moment where you'd reach for merge instead." → forces a comparison and a teaching arc.

## Setup, runbook, and toolchain

- **Q-001** [tag: runbook, difficulty: easy]
  - **Q:** A new teammate just cloned this repo and asks you what they need to type to get a working environment. Where do you point them, and what do you tell them about how `mise`, `uv`, and `.env` fit together?
  - **A:** Point them at `mise.toml` at the repo root and `docs/learn-this-project/02-runbook.md` for the full sequence. The commands are `mise install` (installs Python 3.12 and uv per the toml), then `mise run inst` (which shells out to `uv sync --all-extras` to populate `.venv/`), then `cp .env.example .env` and fill in the `AWS_PROFILE` + bucket variables. The reason this project layers `mise` on top of `uv` is that `mise` answers *both* "which Python version?" and "what tasks exist?" in one file — a teammate doesn't have to learn `pyenv` + `uv` + `Makefile` separately. The `.env` step is the often-forgotten one, because half the examples touch S3 and silently break with `KeyError: 'AWS_PROFILE'` if it's missing.
  - **Source:** `mise.toml`, `docs/learn-this-project/02-runbook.md#first-time-setup`

- **Q-002** [tag: knowhow, difficulty: easy]
  - **Q:** A colleague says "I tried `examples/02-polars-etl/s01_column_ops.py` and it ran without setting up AWS — is that a bug?" How do you explain it?
  - **A:** It's by design. The `02-polars-etl/` module is the only one that does pure in-memory Polars work — no `read_delta`, no `write_delta`, no S3. Open any of its three scripts (`s01_column_ops.py`, `s02_dedup_agg.py`, `s03_transform.py`) and you'll see they never import `one` or use `pl.read_delta()`. The reason this module exists separately is pedagogical: build Polars fluency *before* combining it with Delta Lake, so when something later fails you can localize the bug to the Polars half or the Delta half instead of debugging the whole stack.
  - **Source:** `examples/02-polars-etl/`, `docs/learn-this-project/02-runbook.md#running-locally`

- **Q-003** [tag: runbook, difficulty: medium]
  - **Q:** Walk through the "if `__name__ == '__main__'` runs pytest as a subprocess" pattern. Why was it built that way instead of just running `pytest tests/`?
  - **A:** The pattern lives in `delta_lake_and_polars_basic/vendor/pytest_cov_helper.py` and is re-exported via `delta_lake_and_polars_basic/tests/helper.py`. Each test file calls `run_unit_test(__file__)` or `run_cov_test(__file__)`, which uses `subprocess.run(["pytest", "--cov=...", __file__])`. The point is fast iteration during development — you double-click a single test file in your IDE and get an isolated run with coverage scoped to its module, instead of waiting for the full suite. `mise run test` and `mise run cov` are the "run everything" counterparts. The tradeoff is that subprocess-launched pytest is slower than in-process pytest, so this pattern is for dev convenience, not CI throughput.
  - **Source:** `delta_lake_and_polars_basic/vendor/pytest_cov_helper.py`, `CLAUDE.md`

## The `one` singleton and AWS plumbing

- **Q-004** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through what the `one` singleton actually owns and why the codebase routes all AWS access through it instead of letting each example script create its own boto3 session.
  - **A:** Start in `delta_lake_and_polars_basic/one/one_01_main.py` — the `One` class is assembled by mixin composition from three files: `one_02_config.py` (`OneConfigMixin` — placeholder for config knobs), `one_03_boto_ses.py` (`OneBotoSesMixin` — wraps `BotoSesManager` over the `AWS_PROFILE` env var and exposes `bsm`, `s3_client`, and `polars_storage_options`), and `one_04_s3.py` (`OneS3Mixin` — exposes the project's S3 bucket and root `S3Path`). The singleton is exported from `delta_lake_and_polars_basic/one/api.py` as the bare name `one`. Centralizing this means every one of the 16 scripts gets credentials, paths, and Polars storage options from one source — change the bucket once and everything follows. Without it, each script would duplicate ~20 lines of boto3 setup, and `polars_storage_options` (the AWS dict Polars/deltalake need) would be reinvented per script.
  - **Source:** `delta_lake_and_polars_basic/one/one_01_main.py`, `docs/learn-this-project/01-knowhow-inventory.md#one-singleton`

- **Q-005** [tag: knowhow, difficulty: medium]
  - **Q:** Why does `polars_storage_options` extract temporary STS credentials at call time? What's the gotcha?
  - **A:** Look at `delta_lake_and_polars_basic/one/one_03_boto_ses.py` — the property pulls `access_key`, `secret_key`, `session_token`, and `region` off the boto3 credential chain *at the moment it's read*. That's necessary because Polars and `deltalake` don't speak boto3 — they take a flat dict of env-var-style keys to pass through to the underlying Rust S3 client. The gotcha is freshness: if your credentials expire mid-session (typical for SSO/AssumeRole), the cached dict still holds the stale token and writes start failing with `ExpiredToken`. In a long-running process you'd want to re-read `one.polars_storage_options` each operation rather than cache it once.
  - **Source:** `delta_lake_and_polars_basic/one/one_03_boto_ses.py`, `docs/learn-this-project/01-knowhow-inventory.md#one-singleton`

- **Q-006** [tag: knowhow, difficulty: hard]
  - **Q:** The Polars storage options set `AWS_S3_ALLOW_UNSAFE_RENAME=true`. Walk through what that flag turns off, why this project is okay setting it, and what would break if you reused this pattern at production scale.
  - **A:** `AWS_S3_ALLOW_UNSAFE_RENAME` is a delta-rs flag that bypasses the DynamoDB-based locking mechanism Delta Lake normally uses to serialize concurrent commits on S3. The setting is wired in `delta_lake_and_polars_basic/one/one_03_boto_ses.py`. This POC is safe because every example is a single-writer process — you run one script at a time, and idempotent S3 directory deletion at the top of each script guarantees no other writer is racing. In production with two ETL jobs trying to commit to the same Delta table at once, the unsafe-rename setting lets both succeed at the S3 layer but with no coordination — you'd end up with a corrupted `_delta_log` (two version-N JSON files, only one survives), losing one writer's data silently. The fix is to wire a DynamoDB lock client or use an S3 backend that supports conditional writes.
  - **Source:** `delta_lake_and_polars_basic/one/one_03_boto_ses.py`, `docs/learn-this-project/03-elevation-roadmap.md`

## Delta Lake fundamentals (01-delta-read-write)

- **Q-007** [tag: knowhow, difficulty: medium]
  - **Q:** Why do `s02_append.py` and the merge examples coexist in the curriculum? Walk through what append does, what it deliberately *doesn't* do, and the moment where you'd reach for merge instead.
  - **A:** Open `examples/01-delta-read-write/s02_append.py` — it writes 3 rows, then writes 2 more with `mode="append"`, one of which has a duplicate `id`. The Delta table ends with 5 rows including the dupe. That's the point: append is a *literal* append — no key, no dedup, no concept of "row identity". `examples/03-merge-upsert/s01_basic_upsert.py` is the contrast — it uses `.merge(source, predicate, source_alias, target_alias).when_matched_update_all().when_not_matched_insert_all().execute()` and dedups via the predicate. You reach for merge the instant your data has natural keys and incoming batches can re-state existing rows (e.g. transaction status changing from `AUTHORIZED` → `SETTLED`). Beginners who expect "INSERT OR UPDATE" semantics from append are the target audience for this comparison.
  - **Source:** `examples/01-delta-read-write/s02_append.py`, `examples/03-merge-upsert/s01_basic_upsert.py`

- **Q-008** [tag: knowhow, difficulty: medium]
  - **Q:** What does `mode="error"` give you that `mode="overwrite"` doesn't? Walk through a scenario where shipping with the wrong one causes silent damage.
  - **A:** `mode="error"` in `examples/01-delta-read-write/s03_error_mode.py` raises `DeltaError` if the table already exists at the URI — the second `write_delta` call in that script intentionally fails to demonstrate it. `mode="overwrite"` would silently replace whatever was there. Imagine a daily ETL that's *supposed* to write a brand-new partition each day, but a bug accidentally writes today's data to yesterday's URI — with `overwrite` you've lost yesterday silently and only discover it during the next audit; with `error` the job blows up on day two and you fix the URI bug before any data is destroyed. So `error` is the "guard rail" mode for fresh-write workflows; `overwrite` is for "I really do mean to clobber" workflows like full-recompute Gold tables.
  - **Source:** `examples/01-delta-read-write/s03_error_mode.py`

## Polars ETL patterns (02-polars-etl)

- **Q-009** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through how `s03_transform.py` builds its SHA-256 PII-masking pattern. Why was it designed that way and where does it reappear later in the curriculum?
  - **A:** Open `examples/02-polars-etl/s03_transform.py` — the masking is `pl.col("card_id").map_elements(lambda v: hashlib.sha256(v.encode()).hexdigest()[:16], return_dtype=pl.Utf8)` chained inside a `with_columns(...)`. It uses `map_elements` (per-row Python callable) rather than a vectorized Polars expression because `hashlib` doesn't vectorize — there's no `pl.sha256` built-in. The 16-char truncation is enough to keep cardinality high while collapsing the column footprint. The same pattern reappears verbatim in `examples/06-full-etl/s02_silver_etl.py` to mask `card_id` during the Bronze→Silver pass. Teaching it first as a standalone Polars exercise (no S3) keeps the lesson focused; reusing it inside the full ETL shows you how a small transformation composes into a real pipeline.
  - **Source:** `examples/02-polars-etl/s03_transform.py`, `examples/06-full-etl/s02_silver_etl.py`

- **Q-010** [tag: knowhow, difficulty: medium]
  - **Q:** Why is `df.unique(subset=[...], keep="first")` the right primitive for dedup in this project, and what would go wrong if you reached for `group_by(...).agg(pl.first())` instead?
  - **A:** `examples/02-polars-etl/s02_dedup_agg.py` and `examples/06-full-etl/s02_silver_etl.py` both use `df.unique(subset=["transaction_id"], keep="first")` because Polars has a dedicated, optimized dedup primitive — it's both more readable and more efficient than a group-by. A `group_by("transaction_id").agg(pl.first())` would *technically* dedup but would also reshape every other column into a scalar-per-group, which is fragile when schemas change (you have to enumerate every column in the agg). `unique` keeps the full row schema and just picks a row per key. The "keep first" choice matters: in the ETL, the first occurrence of a transaction id wins, so source ordering becomes a semantic decision — Bronze appends in arrival order, so "first" effectively means "earliest seen", which matches the ETL's intent.
  - **Source:** `examples/02-polars-etl/s02_dedup_agg.py`, `examples/06-full-etl/s02_silver_etl.py`

- **Q-011** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through `pl.when().then().otherwise()` as it appears in this codebase. How does it compare to Pandas/SQL approaches, and why does the chained `with_columns` style matter?
  - **A:** In `examples/02-polars-etl/s03_transform.py` you'll find `pl.when(pl.col("status") == "DECLINED").then(pl.lit(0)).otherwise(pl.col("amount"))` — essentially a SQL `CASE WHEN`. In Pandas you'd write `df["amount"] = np.where(...)` which mutates in place; the Polars version is an *expression* that lives inside `with_columns(...)`, so the whole transformation is a value, not a side effect. That's important because `with_columns(expr1, expr2, expr3)` builds one optimized query plan — Polars's lazy engine can fuse and parallelize the steps. The chained style also makes the script read top-down: "given a row, derive these columns from these expressions, return a new DataFrame." No hidden mutation, no `SettingWithCopyWarning`.
  - **Source:** `examples/02-polars-etl/s03_transform.py`

## Merge / upsert (03-merge-upsert)

- **Q-012** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through the merge predicate string `"target.id = source.id"` in `s01_basic_upsert.py`. Where do `target` and `source` come from, and what's the easiest way to get this wrong?
  - **A:** Open `examples/03-merge-upsert/s01_basic_upsert.py` — the call shape is `dt.merge(source=df, predicate="target.id = source.id", source_alias="source", target_alias="target")`. The two alias arguments are what make `target` and `source` legal identifiers inside the predicate string — without them, the SQL parser doesn't know which side `id` refers to. The predicate is a string, not a Python expression, so typos like `taget.id` or using the wrong column name fail at execute time, not at parse time. The other common foot-gun is forgetting that both sides need the column — if `source` is missing `id` you get a column-not-found error that points at the predicate, not at the source DataFrame. For more complex matches you can AND additional conditions in the same string, e.g. `target.id = source.id AND target.tenant = source.tenant`.
  - **Source:** `examples/03-merge-upsert/s01_basic_upsert.py`

- **Q-013** [tag: knowhow, difficulty: medium]
  - **Q:** In `s02_credit_profile.py` the test asserts the post-merge row count is 220 (200 baseline + 50 source = 30 updates + 20 inserts). Walk through why the math is `200 + 20`, not `200 + 50` or `30 + 20`, and what the assertion is really checking.
  - **A:** Look at `examples/03-merge-upsert/s02_credit_profile.py` — the source has 50 rows; of those, 30 share an `id` with the 200-row target (so they update the existing rows in place — count unchanged), and 20 are new ids (so they're inserted — count +20). Final = 200 + 20 = 220. The assertion is checking that merge respected matched-vs-unmatched semantics and didn't accidentally duplicate the 30 overlapping rows (which would give 250) or skip the 20 unmatched ones (which would give 200). The script also verifies specific updated field values and untouched rows, which is the more interesting test — row count alone wouldn't catch a bug where merge wrote *wrong* updates to the right rows.
  - **Source:** `examples/03-merge-upsert/s02_credit_profile.py`

## Time travel (04-time-travel)

- **Q-014** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through what "version 0" means in `examples/04-time-travel/s01_version_read.py`. A common misconception is that v0 is an empty table — how would you correct that?
  - **A:** Open `s01_version_read.py` — the script writes three times, then reads each version with `pl.read_delta(uri, version=N, storage_options=...)` for N in `{0, 1, 2}`. Version 0 is the **first commit**, which already contains the rows from the first write — not an empty pre-state. Delta Lake doesn't have a "before any data" version; the table exists when its first commit lands. The conceptual model is that the `_delta_log/` directory is a sequence of JSON commit files starting at `00000000000000000000.json` (version 0), and each one describes a set of file adds/removes relative to the prior state. So "v0" answers "what did this table look like immediately after creation?", and a query against a non-existent version (e.g. `version=99`) raises an error rather than returning empty.
  - **Source:** `examples/04-time-travel/s01_version_read.py`

- **Q-015** [tag: knowhow, difficulty: medium]
  - **Q:** What does `DeltaTable.history()` actually return, and what would you use it for in production besides the demo print?
  - **A:** In `examples/04-time-travel/s02_history.py` the call is `dt.history()` and returns a list of dicts — one per commit — with at least `version`, `timestamp`, and `operation` (e.g. `"WRITE"`, `"MERGE"`). For a regulator-friendly audit trail, you can replay or attest to the table state as-of any historical moment: "show me what this customer's credit profile looked like on Jan 15" becomes `dt.load_as_version(version_at_timestamp("2026-01-15"))`. For operational use, you tail the history to detect unexpected operations (e.g. a `MERGE` you didn't authorize) or to roll back a bad write by reading the prior version and re-writing it. The history is also what makes vacuum safe — until you vacuum, every historical version is replayable.
  - **Source:** `examples/04-time-travel/s02_history.py`

## Vacuum and schema evolution (05-vacuum-schema)

- **Q-016** [tag: knowhow, difficulty: hard]
  - **Q:** `s01_vacuum.py` calls vacuum with `retention_hours=0` and `enforce_retention_duration=False`. Walk through what each flag does, why this script uses the unsafe combo, and the production rule you should follow instead.
  - **A:** Look at `examples/05-vacuum-schema/s01_vacuum.py`. `retention_hours` is the minimum age of a Parquet file before vacuum will delete it; `enforce_retention_duration` is a safety check that, when `True` (the default), refuses any value below 168 hours (one week). Setting it `False` lets you pass `retention_hours=0` so the demo can show files disappearing immediately. In production this combination is dangerous because a concurrent reader holding an open snapshot to a now-vacuumed file gets `FileNotFoundError` mid-query, and time travel beyond the retention window also breaks. The production rule is `retention_hours=168` (one week, the Delta default) and leave `enforce_retention_duration=True`; if you need to vacuum more aggressively, do it during a maintenance window where you know no readers are active.
  - **Source:** `examples/05-vacuum-schema/s01_vacuum.py`

- **Q-017** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through `s02_schema_evolution.py`. What does `schema_mode="merge"` do, and what's the implicit promise it makes to existing readers?
  - **A:** Open `examples/05-vacuum-schema/s02_schema_evolution.py` — it writes 3 rows with schema `(id, name)`, then appends 2 rows with `(id, name, email)` using `delta_write_options={"schema_mode": "merge"}`. After the append, the table schema is `(id, name, email)` and the original 3 rows have `email=null`. The promise: existing readers that select only the original columns keep working unchanged — adding a column is a backwards-compatible operation. Without `schema_mode="merge"`, the second write would raise a schema mismatch error. The asymmetric case is column *removal* or type *narrowing*, which would break readers and isn't supported by simple merge — those require explicit `schema_mode="overwrite"` and you have to take the breakage as a deliberate decision.
  - **Source:** `examples/05-vacuum-schema/s02_schema_evolution.py`

## Full ETL pipeline (06-full-etl)

- **Q-018** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through the Bronze→Silver split as it's implemented in `06-full-etl`. Why are they separate tables instead of one transformed table, and what would you lose by collapsing them?
  - **A:** `examples/06-full-etl/s01_bronze_write.py` reads `data/batch_1.json` (10 raw transactions) and writes them verbatim to a Bronze Delta table. `s02_silver_etl.py` reads all of Bronze, dedups on `transaction_id`, SHA-256-masks `card_id`, filters out `DECLINED`, adds `etl_ts`, and writes 7 rows to Silver. Keeping Bronze as the raw landing zone means you can re-derive Silver with a new ETL definition (e.g. change the masking algorithm) without re-ingesting raw data — Bronze becomes the immutable system-of-record. Collapsing them would couple ingestion latency to ETL latency, force every schema change to be retroactive, and lose the ability to backfill Silver from history. The pattern is canonical in lakehouse architectures (medallion: bronze/silver/gold).
  - **Source:** `examples/06-full-etl/s01_bronze_write.py`, `examples/06-full-etl/s02_silver_etl.py`

- **Q-019** [tag: knowhow, difficulty: hard]
  - **Q:** In `s03_incremental.py` the Silver step re-reads ALL of Bronze instead of just the new batch. Walk through why the author made that choice and what production change you'd push for once the data volume grew.
  - **A:** Open `examples/06-full-etl/s03_incremental.py` — it appends `batch_2.json` to Bronze, then re-runs the *entire* `s02_silver_etl.py` logic (full read + dedup + mask + filter) and merges the result into Silver. The "full recompute, then merge" pattern is simpler to reason about: you never have to ask "did I miss a row?" because the dedup pass naturally absorbs duplicates from any number of overlapping batches. The cost scales as O(total Bronze rows) per run, which is fine at POC scale but blows up at production volume. The senior-engineer upgrade is CDC (change data capture): track which rows are new since the last Silver build (via a watermark column or Delta's `_change_data` feed) and only transform those, which scales as O(new rows). See `docs/learn-this-project/03-elevation-roadmap.md` for the full pitch.
  - **Source:** `examples/06-full-etl/s03_incremental.py`, `docs/learn-this-project/03-elevation-roadmap.md#cdc`

- **Q-020** [tag: knowhow, difficulty: medium]
  - **Q:** `s03_incremental.py` verifies the merge by comparing Silver version 0 against version 1 via time travel. Walk through what the comparison proves and why it's a stronger test than just checking row counts.
  - **A:** Look at `examples/06-full-etl/s03_incremental.py` — after the merge it reads `pl.read_delta(silver_uri, version=0, ...)` (pre-merge Silver, 7 rows) and `pl.read_delta(silver_uri, version=1, ...)` (post-merge, 10 rows after merging 3 new + 2 updates). Row counts alone could be satisfied by 7+3=10 with no updates applied — wrong. Field-by-field comparison on the overlapping `transaction_id`s shows that `amount` was updated, proving merge applied `when_matched_update_all`. This pattern is the Delta-specific equivalent of "diff your test against a known baseline" — you don't need a separate test database because time travel gives you a free baseline.
  - **Source:** `examples/06-full-etl/s03_incremental.py`

- **Q-021** [tag: knowhow, difficulty: medium]
  - **Q:** Why does `s02_silver_etl.py` add `etl_ts = pl.lit(current_timestamp).alias("etl_ts")` instead of letting Delta Lake record the write time? What does `etl_ts` give you that `dt.history()` doesn't?
  - **A:** In `examples/06-full-etl/s02_silver_etl.py` the `with_columns(pl.lit(datetime.now()).alias("etl_ts"))` stamps every row with the time the ETL pass ran. `dt.history()` records when *commits* happened — that's a per-version timestamp, not a per-row one. Per-row `etl_ts` lets downstream consumers ask "show me Silver rows produced after 14:00 yesterday" with a simple filter, which is critical for monitoring (catching when an ETL pass stalled) and for incremental downstream pipelines (Gold reads Silver where `etl_ts > last_seen`). Tying provenance to the row rather than the commit also survives operations like `OPTIMIZE` or `VACUUM` that rewrite the underlying files.
  - **Source:** `examples/06-full-etl/s02_silver_etl.py`

## Conventions and cross-cutting patterns

- **Q-022** [tag: convention, difficulty: easy]
  - **Q:** Every example script starts by deleting its own S3 directory. Walk through why the idempotent-startup convention exists and what would go wrong without it.
  - **A:** Look at the top of nearly any script in `examples/`, e.g. `examples/01-delta-read-write/s01_overwrite.py` — it calls `s3dir_example.delete(bsm=bsm)` before writing anything. The convention exists because learners run scripts repeatedly while experimenting, and Delta Lake remembers state across runs (commit log + active Parquet files). Without idempotent cleanup, the second run of an "overwrite mode" demo would see leftover state from version N-1, producing confusing version numbers and history outputs that don't match the script's narrative. The pattern is safe because each script owns a unique S3 subdirectory under the project's root prefix — you can't accidentally delete someone else's data.
  - **Source:** `examples/01-delta-read-write/s01_overwrite.py`, `docs/learn-this-project/01-knowhow-inventory.md#conventions`

- **Q-023** [tag: convention, difficulty: easy]
  - **Q:** Why do the scripts print `s3dir_example.console_url` near the start of execution? What's the principle behind exposing this?
  - **A:** Open any script and search for `console_url` — e.g. `examples/00-minimal-poc/s01_minimal_poc.py`. The URL is the AWS S3 Console deep-link to the script's working directory. Printing it makes the script self-debuggable: when something looks wrong in the output, the learner can click the URL and visually inspect the `_delta_log/` JSON files and the Parquet data files in the browser. The principle is "make the side effects observable" — Delta Lake's whole value is that table state is fully captured in S3 files, so giving the user a one-click view turns that into a pedagogical asset.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py`, `delta_lake_and_polars_basic/one/one_04_s3.py`

- **Q-024** [tag: convention, difficulty: medium]
  - **Q:** The `One` class is composed from three mixins instead of a single monolithic class. Walk through what each mixin owns and what the design buys you compared to one big `One` class.
  - **A:** `delta_lake_and_polars_basic/one/one_01_main.py` defines `One` as `class One(OneConfigMixin, OneBotoSesMixin, OneS3Mixin)`. `OneConfigMixin` (in `one_02_config.py`) is a placeholder for runtime config — currently returns `None` but reserves the slot. `OneBotoSesMixin` (in `one_03_boto_ses.py`) owns AWS credentials and the `polars_storage_options` dict. `OneS3Mixin` (in `one_04_s3.py`) owns the bucket name and the root `S3Path`. Splitting them like this lets each concern grow independently — if config evolves into a Pydantic-loaded YAML, only `one_02_config.py` changes; if you swap `BotoSesManager` for something else, only `one_03_boto_ses.py` changes. It also makes each file small and individually testable. The cost is a slightly higher cognitive overhead — "where is `bsm` defined?" — which `api.py` partly mitigates by being the single import surface.
  - **Source:** `delta_lake_and_polars_basic/one/one_01_main.py`, `docs/learn-this-project/01-knowhow-inventory.md#one-singleton`

## Dependency choices

- **Q-025** [tag: deps, difficulty: medium]
  - **Q:** Why does this project use `delta-rs` (the `deltalake` Python package) instead of PySpark's Delta Lake? Walk through the tradeoff and what the project would look like if Spark were in play.
  - **A:** `pyproject.toml` pins `deltalake>=1.5.1,<1.6.0` — the pure-Rust implementation. The motivation is operational: delta-rs lets you read, write, and merge Delta tables from any Python process without a JVM, a Spark cluster, or a SparkSession. For the fintech use case this was extracted from (small-to-mid-volume ETL inside AWS Lambda), Spark is overkill — the cold-start, memory footprint, and cluster management would dwarf the actual work. With Spark you'd swap most of the codebase: scripts become Spark jobs, you have a `SparkSession.builder`, Delta operations go through `delta.tables.DeltaTable`, and you're running on EMR or Databricks. The tradeoff cuts the other way at very large data volumes where Spark's distributed execution starts winning.
  - **Source:** `pyproject.toml`, `docs/learn-this-project/01-knowhow-inventory.md#external-dependencies`

- **Q-026** [tag: deps, difficulty: medium]
  - **Q:** Why `polars` over `pandas` for the ETL layer? Walk through the actual constraints that made this the right call here.
  - **A:** `pyproject.toml` pins `polars>=1.39.3,<1.40.0`. Polars is Rust-based, multi-threaded by default, uses Arrow's columnar memory layout, and supports lazy evaluation — typical 5–10x faster than Pandas on columnar ETL and noticeably stingier on memory. The fintech production deployment runs inside AWS Lambda with strict memory limits and a 15-minute execution cap; Pandas would routinely blow either constraint on gigabyte-scale transaction batches, while Polars finishes comfortably. The teaching project inherits the choice: every example uses Polars idioms (`with_columns`, `pl.col(...).map_elements`, `unique(subset=...)`), so the patterns transfer directly to production. The cost is a smaller ecosystem (fewer plotting integrations, smaller Stack Overflow corpus) but for an ETL-shaped project that doesn't bite.
  - **Source:** `pyproject.toml`, `examples/00-minimal-poc/README.md`

- **Q-027** [tag: deps, difficulty: medium]
  - **Q:** Walk through `s3pathlib` and `boto-session-manager` as third-party dependencies. What problems do they solve, and why pull them in instead of using raw boto3?
  - **A:** Both are author-authored libraries that wrap boto3 in more ergonomic interfaces. `s3pathlib` (`S3Path` type) gives S3 keys a `pathlib`-style API — `S3Path("s3://b/k").joinpath("sub").delete()` reads cleanly, whereas raw boto3 is `s3.delete_object(Bucket=..., Key=...)` with manual key concatenation. It's used in `delta_lake_and_polars_basic/one/one_04_s3.py` to expose `s3dir_root` as an `S3Path`. `boto-session-manager` (`BotoSesManager`) collapses boto3's verbose credential chain into a one-liner with cached properties for `s3_client`, `boto_ses`, `region_name`, etc. — used in `one_03_boto_ses.py`. Both reduce the boilerplate per example script and make the `one` singleton small. The risk is dependency lock-in to one author's libraries, which the elevation roadmap could flag as a long-term concern.
  - **Source:** `delta_lake_and_polars_basic/one/one_03_boto_ses.py`, `delta_lake_and_polars_basic/one/one_04_s3.py`

## Cross-module synthesis

- **Q-028** [tag: mech, difficulty: hard]
  - **Q:** Trace what physically happens on S3 when `s02_credit_profile.py` runs end-to-end. Walk from the initial write through the merge, naming what lands in `_delta_log/` and what happens to the Parquet files.
  - **A:** Look at `examples/03-merge-upsert/s02_credit_profile.py`. The 200-row baseline write creates `00000000000000000000.json` in `_delta_log/` (version 0, operation `WRITE`) and one or more `part-*.parquet` files containing the 200 rows. The merge then runs: delta-rs reads the affected Parquet files into memory, applies the 30 updates and 20 inserts, writes *new* Parquet files for the rewritten partitions, and commits `00000000000000000001.json` (version 1, operation `MERGE`) recording which old files were removed and which new ones were added. The old Parquet files are still on S3 — vacuum hasn't been called — and remain accessible via time travel (`pl.read_delta(uri, version=0)`). This is why the `_delta_log` is the "magic": the Parquet files are immutable; "updates" are just new files plus a commit that swaps which ones are live.
  - **Source:** `examples/03-merge-upsert/s02_credit_profile.py`, `examples/00-minimal-poc/README.md`

- **Q-029** [tag: knowhow, difficulty: hard]
  - **Q:** A reviewer says "this project teaches Polars, Delta Lake, and S3 — but where is the actual *production* lesson?" Walk through what production-relevant patterns the examples teach beyond the API surface.
  - **A:** Beyond API mechanics, the project teaches several production-shaped patterns. (1) The idempotent-startup convention (delete S3 dir, rebuild) at the top of every script models how to write rerunnable batch jobs — production ETL needs to survive retries without duplicating data. (2) The Bronze/Silver split in `06-full-etl` models the medallion architecture: raw landing layer + cleaned/transformed layer with explicit ETL between them. (3) The PII-masking pattern (`map_elements(sha256(...)[:16])`) in `02-polars-etl/s03_transform.py` and reused in Silver shows how compliance constraints translate into deterministic transformations that downstream joins can still use. (4) The merge-then-time-travel verification in `s03_incremental.py` shows audit-friendly verification. (5) The `one` singleton centralizing AWS config models how you'd structure shared infra for a real service. The deliberate omissions (no tests, no CI, no observability) are *also* lessons — they're surfaced in `03-elevation-roadmap.md` as the next-maturity steps.
  - **Source:** `docs/learn-this-project/03-elevation-roadmap.md`, `examples/06-full-etl/`

- **Q-030** [tag: knowhow, difficulty: hard]
  - **Q:** Walk through how schema evolution (`s02_schema_evolution.py`), time travel (`04-time-travel/`), and merge (`03-merge-upsert/`) all rely on the same underlying Delta Lake mechanism. What is that mechanism, and what would you lose if any one of those features broke?
  - **A:** All three rest on the `_delta_log/` transaction log — a directory of JSON commit files that describe Parquet adds/removes per commit, replayed in order to compute the current table state. Schema evolution: each commit records the table schema; `schema_mode="merge"` writes a commit that declares the new wider schema, and replaying commits 0..N gives you the per-version schema. Time travel: reading at version N stops the replay at commit N, so you reconstruct the table as it was. Merge: delta-rs reads current state, computes target Parquet file deltas, writes a single new commit recording removes + adds — atomic. If the log broke (e.g. a missing commit JSON), all three features fail: schema evolution can't be replayed, time travel can't reach the missing version, merge can't safely identify what to remove. The log *is* the database, with the Parquet files acting as the value store.
  - **Source:** `examples/04-time-travel/s02_history.py`, `examples/05-vacuum-schema/s02_schema_evolution.py`, `examples/00-minimal-poc/README.md`

## CI / docs / packaging

- **Q-031** [tag: runbook, difficulty: medium]
  - **Q:** Walk through what `.github/workflows/main.yml` actually runs on a push. What's gated by CI, and what isn't?
  - **A:** Open `.github/workflows/main.yml` and `02-runbook.md` together. CI installs the toolchain via the mise setup, runs `mise run cov` (pytest with coverage scoped to the `delta_lake_and_polars_basic/` package), and uploads coverage to codecov.io per `codecov.yml`. What's gated: the package-level unit tests and coverage threshold. What's *not* gated: the example scripts — none of them run in CI (no AWS credentials available in the CI environment, and they're not wrapped in pytest tests). That's a deliberate gap the elevation roadmap flags as "add a `tests/test_examples.py` that smoke-runs each script against moto or MinIO". So a broken example would ship green on CI today — discovering it depends on a human running the script locally.
  - **Source:** `.github/workflows/main.yml`, `docs/learn-this-project/03-elevation-roadmap.md#test-depth`

- **Q-032** [tag: runbook, difficulty: easy]
  - **Q:** A teammate asks "how do I add this package as a dependency in another project?" Walk through what would and wouldn't work today.
  - **A:** Look at `pyproject.toml` — the package name is `delta_lake_and_polars_basic`, version `0.1.1`, with build config via `mise run build` (creates wheel + sdist in `dist/`) and `mise run publish` (uploads to PyPI with `PYPI_TOKEN`). So technically yes, another project could `uv add delta_lake_and_polars_basic` once it's published. But the package's public surface is small and POC-oriented — the `one` singleton expects specific env vars (`AWS_PROFILE` and the bucket config), so any consumer has to set up the same `.env` shape. In practice this project is consumed by *reading* the examples and copying the patterns, not by importing it as a library. That's a reasonable design for a learning repo; making it a real reusable library would require a different `one` (configurable, not env-coupled) and a tighter public API.
  - **Source:** `pyproject.toml`, `mise.toml`

- **Q-033** [tag: runbook, difficulty: medium]
  - **Q:** Walk through how documentation is built and hosted for this project. What changes when you edit a file in `docs/source/`?
  - **A:** `.readthedocs.yml` wires the project to readthedocs.org. `docs/source/conf.py` is the Sphinx configuration. The build command is `mise run build-doc`, which runs Sphinx and outputs HTML to `docs/build/html/`. `mise run view-doc` opens the built docs in the browser for local preview. Note that `docs/learn-this-project/` (this directory) is *not* part of the Sphinx build — it's a separate knowledge base consumed by the `learn-this-project-*` skills, not by readers of the published docs site.
