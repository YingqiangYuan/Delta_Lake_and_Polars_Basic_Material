- **Q-002** [tag: convention] [difficulty: easy]
  - **Q:** What is the idempotent startup pattern used in every example script?
  - **A:** Each script calls `s3dir_example.delete(bsm=bsm)` at the top to delete the S3 directory, then rebuilds from scratch. This means scripts can be rerun indefinitely.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md#examples`

- **Q-003** [tag: deps] [difficulty: easy]
  - **Q:** Why does this project use `polars` instead of `pandas`?
  - **A:** Polars is Rust-based and faster than Pandas for columnar operations. The production workloads are columnar ETL where Polars outperforms significantly.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md#external-dependencies`

- **Q-004** [tag: deps] [difficulty: easy]
  - **Q:** Why does this project use `deltalake` (delta-rs) instead of PySpark's Delta Lake?
  - **A:** delta-rs is a pure Rust implementation with no JVM/Spark dependency. It avoids the operational overhead of a Spark cluster.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md#external-dependencies`

- **Q-005** [tag: knowhow] [difficulty: medium]
  - **Q:** What does `AWS_S3_ALLOW_UNSAFE_RENAME=true` do in the Polars storage options, and why is it used here?
  - **A:** It skips DynamoDB-based locking for Delta Lake commits on S3. It's used because this is a single-writer POC. In multi-writer production, this would be dangerous.
  - **Source:** `delta_lake_and_polars_basic/one/one_03_boto_ses.py`

- **Q-009** [tag: knowhow] [difficulty: medium]
  - **Q:** What are the three Delta Lake write modes demonstrated in `01-delta-read-write`?
  - **A:** `overwrite` (replace all data), `append` (add rows without dedup), and `error` (fail if table exists).
  - **Source:** `examples/01-delta-read-write/`

- **Q-010** [tag: knowhow] [difficulty: medium]
  - **Q:** Does `mode="append"` deduplicate rows? What's the implication?
  - **A:** No. Append adds all rows including duplicates. If you need dedup, you must use merge/upsert instead.
  - **Source:** `examples/01-delta-read-write/s02_append.py`

- **Q-011** [tag: knowhow] [difficulty: easy]
  - **Q:** In the merge/upsert pattern, what do `when_matched_update_all()` and `when_not_matched_insert_all()` do?
  - **A:** `when_matched_update_all()` updates existing rows where the merge predicate matches. `when_not_matched_insert_all()` inserts new rows that don't match any existing row.
  - **Source:** `examples/03-merge-upsert/s01_basic_upsert.py`

- **Q-012** [tag: knowhow] [difficulty: medium]
  - **Q:** What string format does the merge predicate use? Give an example.
  - **A:** SQL-like syntax with aliases: `"target.id = source.id"` where `target_alias` and `source_alias` are set in the `merge()` call.
  - **Source:** `examples/03-merge-upsert/s01_basic_upsert.py`

- **Q-013** [tag: knowhow] [difficulty: medium]
  - **Q:** In `s02_credit_profile.py`, how many rows exist after merging a 50-row source (30 updates + 20 inserts) into a 200-row baseline?
  - **A:** 220 rows. The 30 matched rows are updated in-place; the 20 unmatched rows are inserted; the 170 untouched rows remain.
  - **Source:** `examples/03-merge-upsert/s02_credit_profile.py`

- **Q-015** [tag: knowhow] [difficulty: medium]

- **Q-016** [tag: knowhow] [difficulty: hard]
  - **Q:** Why is `retention_hours=0` with `enforce_retention_duration=False` dangerous in production?
  - **A:** It deletes ALL orphaned Parquet files immediately, including those that concurrent readers might still be accessing. Production should use 168+ hours (1 week).
  - **Source:** `examples/05-vacuum-schema/s01_vacuum.py`

- **Q-017** [tag: knowhow] [difficulty: medium]
  - **Q:** How does schema evolution work in `s02_schema_evolution.py`? What happens to old rows when a new column is added?
  - **A:** Using `delta_write_options={"schema_mode": "merge"}`, the new column is added to the schema. Old rows get `null` for the new column.
  - **Source:** `examples/05-vacuum-schema/s02_schema_evolution.py`

- **Q-018** [tag: knowhow] [difficulty: medium]
  - **Q:** What is the Bronze-to-Silver pattern in `06-full-etl`?
  - **A:** Bronze stores raw data as-is. Silver applies ETL: dedup, PII masking, filtering bad records, adding metadata. Bronze is append-only; Silver uses merge for incremental updates.
  - **Source:** `examples/06-full-etl/`

- **Q-019** [tag: knowhow] [difficulty: hard]
  - **Q:** In the Silver ETL, what four transformations are applied to Bronze data?
  - **A:** 1) Dedup on `transaction_id` (keep first). 2) SHA-256 hash on `card_id` for PII masking. 3) Filter out `DECLINED` transactions. 4) Add `etl_ts` timestamp column.
  - **Source:** `examples/06-full-etl/s02_silver_etl.py`

- **Q-020** [tag: knowhow] [difficulty: hard]
  - **Q:** In `s03_incremental.py`, why does the script re-read ALL of Bronze instead of just the new batch?
  - **A:** It uses a "full recompute Silver" pattern — re-applies the entire ETL pipeline then merges. This is simpler but scales as O(total_rows). A CDC approach would be more efficient.
  - **Source:** `examples/06-full-etl/s03_incremental.py`

- **Q-028** [tag: knowhow] [difficulty: medium]
  - **Q:** What Polars function is used for PII masking in this project, and what does it do?

  - **Source:** `examples/02-polars-etl/s03_transform.py`, `examples/06-full-etl/s02_silver_etl.py`
