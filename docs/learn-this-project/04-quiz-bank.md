# 04 — Quiz Bank

## How these questions are designed

These items are **discussion prompts**, not fill-in-the-blank trivia. Each question opens up a topic; each expected answer is **3–5 sentences** that names file paths AND explains the underlying principle (知其然知其所以然 — know-what AND know-why). When grading:

1. Questions are discussion prompts, not fill-in-the-blank.
2. A good answer is 3–5 sentences that names file paths AND explains the principle.
3. If a question can be answered in one sentence, the question was too narrow — that means the question itself failed, not the answerer.

### What good vs bad questions look like

- ❌ Bad: "Which command installs the dependencies?" → forces recital of `mise run inst`. Pure memorization.
- ✅ Good: "A new contributor asks how to get a working environment — where do you point them and what would you tell them about how `mise`, `uv`, and `.env` fit together?" → forces opening `mise.toml`, explaining the layering, and surfacing the `AWS_PROFILE` dependency.

- ❌ Bad: "What is the `one` singleton?" → one-line definition.
- ✅ Good: "Walk through what the `one` singleton actually owns and why the codebase routes all AWS access through it instead of letting each script create its own boto3 session." → forces a tour of the mixin files, with the consolidation rationale.

- ❌ Bad: "Does `mode='append'` deduplicate?" → recall.
- ✅ Good: "Why do `s02_append.py` and the merge examples coexist in the curriculum? Walk through what append does, what it deliberately *doesn't* do, and the moment where you'd reach for merge instead." → forces a comparison and a teaching arc.

## A. Setup, toolchain, and runbook

- **Q-001** [tag: runbook, difficulty: easy]
  - **Q:** A new teammate just cloned this repo and asks you what they need to type to get a working environment. Where do you point them, and what do you tell them about how `mise`, `uv`, and `.env` fit together?
  - **A:** Point them at `mise.toml` at the repo root and `docs/learn-this-project/02-runbook.md` for the full sequence. They'd type `mise install` (which installs Python 3.12 and uv per the toml), then `mise run inst` (which shells out to `uv sync --all-extras` to populate `.venv/`), then `cp .env.example .env` and set `AWS_PROFILE`. The reason this project layers `mise` on top of `uv` is that `mise` answers both "which Python version?" and "what tasks exist?" in one file — a teammate doesn't have to learn `pyenv` + `uv` + `Makefile` separately. The `.env` step is the often-forgotten one, because half the examples touch S3 and silently break with `KeyError: 'AWS_PROFILE'` if it's missing.
  - **Source:** `mise.toml`, `docs/learn-this-project/02-runbook.md#first-time-setup`

- **Q-002** [tag: knowhow, difficulty: easy]
  - **Q:** A colleague says "I tried `examples/02-polars-etl/s01_column_ops.py` and it ran without setting up AWS — is that a bug?" How do you explain it?
  - **A:** It's by design. The `02-polars-etl/` module is the only one that does pure in-memory Polars work — no `read_delta`, no `write_delta`, no S3. Open any of its three scripts (`s01_column_ops.py`, `s02_dedup_agg.py`, `s03_transform.py`) and you'll see they never import `one` or use `pl.read_delta()`. The reason this module exists separately is pedagogical: build Polars fluency *before* combining it with Delta Lake, so when something later fails you can localize the bug to the Polars half or the Delta half instead of debugging the whole stack.
  - **Source:** `examples/02-polars-etl/`, `docs/learn-this-project/01-knowhow-inventory.md#2-3-module-02-polars-etl-pure-polars-no-delta-no-s3`

- **Q-003** [tag: runbook, difficulty: medium]
  - **Q:** Walk through the "subprocess pytest with per-module coverage" pattern. Why was it built that way instead of just running `pytest tests/`?
  - **A:** The pattern lives in `delta_lake_and_polars_basic/vendor/pytest_cov_helper.py` and is re-exported via `delta_lake_and_polars_basic/tests/helper.py`. Each test file calls `run_cov_test(__file__, "<module>")`, which uses `subprocess.run(["pytest", "--cov=<module>", ...])`. The point is fast iteration during development — you double-click a single test file in your IDE and get an isolated run with coverage scoped to its module, instead of waiting for the whole project to be measured. `mise run cov` is the "run everything" counterpart. The tradeoff is that subprocess-launched pytest is slower than in-process pytest, so this pattern is for dev convenience, not CI throughput.
  - **Source:** `delta_lake_and_polars_basic/vendor/pytest_cov_helper.py`, `delta_lake_and_polars_basic/tests/helper.py`, `CLAUDE.md`

- **Q-004** [tag: runbook, difficulty: medium]
  - **Q:** What's the *recommended* order to run the example modules and why isn't it just numeric `00 → 01 → 02 → … → 06`?
  - **A:** The runbook recommends `02-polars-etl/` first, then `00-minimal-poc/`, then `01 → 03 → 04 → 05 → 06`. The reason `02` jumps ahead is that it's the only module that *doesn't* touch S3 — a learner can confirm Polars works before fighting AWS credentials. After that, `00-minimal-poc/` is the round-trip golden reference. The rest follow the numeric order because each subsequent module assumes the previous concept (`03` merge assumes you've seen `01` writes; `06` capstone composes everything).
  - **Source:** `docs/learn-this-project/02-runbook.md#running-locally-the-16-example-scripts`, `examples/README.md`

- **Q-005** [tag: deps, difficulty: medium]
  - **Q:** Why are `polars` and `deltalake` pinned to such narrow version ranges (`polars>=1.39.3,<1.40.0`, `deltalake>=1.5.1,<1.6.0`) when most projects pin to major versions only?
  - **A:** Both libraries are pre-2.0 and frequently change APIs across *minor* versions — Polars in particular has rotated method names and signature shapes between 1.38 and 1.40. The pyproject pins (`pyproject.toml` lines ~30–35) protect the examples from silently breaking when `uv sync` resolves a new minor. A senior version would unpin in CI to catch upstream regressions, but for a teaching repo where every example must keep running, a narrow pin is the right tradeoff.
  - **Source:** `pyproject.toml#dependencies`, `docs/learn-this-project/01-knowhow-inventory.md#external-dependencies`

- **Q-006** [tag: runbook, difficulty: hard]
  - **Q:** Some `mise.toml` tasks (`release`, `setup-codecov`, `setup-readthedocs`, `update-github-metadata`) shell out to `.mise/tasks/*.py` scripts. What happens if you run `mise run release` in this repo right now, and what does that tell you about the repo's relationship to the author's broader template?

## B. The `one` singleton and AWS plumbing

- **Q-007** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through what the `one` singleton actually owns and why the codebase routes all AWS access through it instead of letting each script create its own boto3 session.
  - **A:** `one` is instantiated in `delta_lake_and_polars_basic/one/one_01_main.py` by composing three mixins — `OneConfigMixin` (placeholder for future config), `OneBotoSesMixin` (boto3 session + frozen-credential dict for Polars), and `OneS3Mixin` (S3 bucket name + root path). Every example script imports it via `from delta_lake_and_polars_basic.one.api import one`. The "single instance" shape exists so a learner configures AWS once (`.env`) and gets the same session, the same bucket, and the same `polars_storage_options` dict in all 16 scripts — without it, each script would duplicate ~20 lines of profile resolution + credential extraction.
  - **Source:** `delta_lake_and_polars_basic/one/one_01_main.py`, `one/api.py`, `docs/learn-this-project/01-knowhow-inventory.md#1-1-one-singleton`

- **Q-008** [tag: knowhow, difficulty: hard]
  - **Q:** The `one/` package uses Python's mixin composition pattern (`class One(OneConfigMixin, OneBotoSesMixin, OneS3Mixin): pass`). Why mixins instead of a single monolithic class, or instead of dependency injection?
  - **A:** Mixins let each capability live in its own file (`one_02_config.py`, `one_03_boto_ses.py`, `one_04_s3.py`) — each ~30 lines, each independently testable. Adding a new capability (e.g., `OneGlueJobMixin` for AWS Glue) is a one-file addition: write a new mixin, add it to the inheritance list in `one_01_main.py`, done. A monolithic class would grow without bound; dependency injection would push the wiring onto every consumer (16 scripts × manual injection) and lose the "singleton imported once" ergonomics. The cost is that learners must understand Python's MRO and `cached_property` to debug an attribute that comes from "somewhere up the chain".
  - **Source:** `delta_lake_and_polars_basic/one/one_01_main.py`, `one/one_02_config.py`, `one/one_03_boto_ses.py`, `one/one_04_s3.py`

- **Q-009** [tag: knowhow, difficulty: hard]
  - **Q:** Open `one/one_03_boto_ses.py` and look at the `polars_storage_options` property. Why does it ship **frozen** credentials (a snapshot dict) instead of just handing Polars the boto3 session?
  - **A:** Polars and `deltalake` are Rust libraries — they don't speak Python's boto3 protocol. They need a flat string-to-string dict (AWS_REGION, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN, AWS_S3_ALLOW_UNSAFE_RENAME) that the underlying Rust S3 client can consume. "Frozen" here means the credentials are resolved-once via `BotoSesManager` (which handles SSO, profile chains, STS) and snapshotted at attribute access. The downside is that long-running scripts can outlive a session-token TTL — for hour-long jobs you'd want to recompute the dict before each write.
  - **Source:** `delta_lake_and_polars_basic/one/one_03_boto_ses.py`

- **Q-010** [tag: knowhow, difficulty: medium]
  - **Q:** `polars_storage_options` includes `AWS_S3_ALLOW_UNSAFE_RENAME="true"`. What does that flag actually do, and why is it acceptable here but dangerous in production?
  - **A:** Delta Lake's S3 commit protocol normally uses a DynamoDB lock table to coordinate atomic commits — S3's lack of native rename atomicity means two concurrent writers could clobber each other. `ALLOW_UNSAFE_RENAME=true` tells deltalake "skip the lock, I promise I'm the only writer". For a single-person learning repo it's harmless (and skips the DynamoDB setup overhead). In production with two Lambda functions appending to the same Bronze table, the flag silently allows two commits at the same version number — data corruption that may not surface until vacuum runs. The elevation roadmap (§D) calls this out as a should-fix.
  - **Source:** `one/one_03_boto_ses.py`, `docs/learn-this-project/03-elevation-roadmap.md#d-production-safety-for-merge-vacuum-the-demo-vs-prod-distinction`

- **Q-011** [tag: knowhow, difficulty: medium]
  - **Q:** `one.s3_bucket` is computed as `{account_alias}-{region}-data`. Why was this pattern chosen instead of a hardcoded bucket name or an env variable?
  - **A:** Look at `one/one_04_s3.py` — `s3_bucket` is a `cached_property` that calls `self.bsm.aws_account_alias` and `self.bsm.aws_region`. A new learner with their own AWS account doesn't have to edit code; their bucket name auto-derives. The pattern assumes you've already provisioned a bucket matching that name (or have permission on one), which is the author's organizational convention. The downside: a learner with a one-off bucket whose name doesn't fit the pattern has to override `s3_bucket` somewhere — there's no easy override hook today.
  - **Source:** `delta_lake_and_polars_basic/one/one_04_s3.py`

- **Q-012** [tag: knowhow, difficulty: medium]
  - **Q:** Why does `delta_lake_and_polars_basic/api.py` exist as an empty file? What convention is it serving?
  - **A:** Each package level has its own `api.py` as the public-import surface — see `delta_lake_and_polars_basic/one/api.py`, which re-exports `one`. The top-level `delta_lake_and_polars_basic/api.py` is currently empty because nothing at the package root is meant to be public yet; consumers import from `one.api`. WHY (best guess; verify with project owner): the author follows a convention where every package has an `api.py` for forward-compatibility, even if it's blank initially.
  - **Source:** `delta_lake_and_polars_basic/api.py`, `delta_lake_and_polars_basic/one/api.py`

- **Q-013** [tag: knowhow, difficulty: easy]
  - **Q:** What does `paths.py` exist for, and why bother with a `PathEnum` class instead of just `pathlib.Path(__file__).parent`?
  - **A:** `delta_lake_and_polars_basic/paths.py` defines a `PathEnum` whose attributes are `cached_property` instances returning absolute `Path` objects (`dir_project_root`, `dir_htmlcov`, etc.). Every consumer (e.g., `tests/helper.py`) imports `path_enum` and uses `path_enum.dir_project_root` — same answer regardless of CWD. The "enum-as-class" shape gives IDE autocomplete on path names (try typing `path_enum.` in an editor), centralizes filesystem layout (move a file → change one place), and avoids the `Path(__file__).absolute().parent.parent.parent` chains that creep in everywhere otherwise.
  - **Source:** `delta_lake_and_polars_basic/paths.py`

## C. Examples — the curriculum, mechanism, and "why this script exists"

- **Q-014** [tag: knowhow, difficulty: medium]
  - **Q:** Every script that writes to S3 starts with `s3dir_example.delete(bsm=bsm)`. Why not check-and-skip if the table exists, or just let Delta overwrite handle it?
  - **A:** Open any example, e.g. `01-delta-read-write/s01_overwrite.py` at the top of `main()`. The cleanup-first idiom makes scripts safe to re-run *for free* — a learner doesn't have to think about prior state, and there's no risk of `mode="error"` failing on a residual table from yesterday. "Check-and-skip" would force every script to grow a 5-line conditional; relying on Delta's `mode="overwrite"` wouldn't reclaim the `_delta_log/` from a previous schema. Delete-then-write is one line and one obvious meaning. The cost is one extra LIST + DELETE per run, which is negligible for tutorial-sized data.
  - **Source:** `examples/01-delta-read-write/s01_overwrite.py`, `examples/00-minimal-poc/s01_minimal_poc.py`

- **Q-015** [tag: knowhow, difficulty: easy]
  - **Q:** Why does `00-minimal-poc/` exist when `01-delta-read-write/` already covers reads and writes? Aren't they doing the same thing?
  - **A:** `00-minimal-poc/s01_minimal_poc.py` is a *golden reference* that compresses read + write + merge into one ~80-line script — it's the single canonical example of the coding conventions (`s3dir_`/`s3path_`/`df_` naming, multi-line `.write_delta(...)`, cleanup-first idempotency). `01-delta-read-write/` then unpacks the same concepts more slowly, one write mode per script. The pedagogical logic: see the whole thing first to know where you're going, then walk through each piece. The verbose `00-minimal-poc/README.md` (~418 lines) provides the broader context — S3, Parquet, Delta Lake architecture, fintech framing.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py`, `examples/00-minimal-poc/README.md`, `examples/01-delta-read-write/`

- **Q-016** [tag: knowhow, difficulty: medium]
  - **Q:** `01-delta-read-write/s02_append.py` deliberately runs append twice on the same data. Why? What's the lesson?
  - **A:** The script does two consecutive `.write_delta(uri, mode="append", ...)` calls with the same DataFrame to demonstrate that append **does not deduplicate** — both batches land, and the result has duplicate rows. That's the teaching point: append is "add these rows unconditionally", not "make sure these rows exist". The setup for the next module (`03-merge-upsert/`) is "if you want deduplication or row-level update semantics, you need merge, not append". A single-run append wouldn't make this visible.
  - **Source:** `examples/01-delta-read-write/s02_append.py`, `examples/03-merge-upsert/`

- **Q-017** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through what `s03_error_mode.py` is teaching. When would you actually use `mode="error"` in production?
  - **A:** `s03_error_mode.py` writes once (succeeds), then attempts a second write with `mode="error"` and catches the `DeltaError` it raises. The lesson is *defensive idempotency*: in a real Lambda pipeline you sometimes want a job that's wired to run exactly-once to *crash loudly* if it accidentally fires twice. `mode="error"` becomes a safety belt for jobs whose retry policy you don't fully trust. The alternative (overwrite or append on retry) silently masks the double-run. The script's `try/except` wrapper is the only one in the entire repo — that's a deliberate signal too.
  - **Source:** `examples/01-delta-read-write/s03_error_mode.py`

- **Q-018** [tag: knowhow, difficulty: medium]
  - **Q:** Compare `02-polars-etl/s01_column_ops.py` and `s02_dedup_agg.py`. What's the teaching arc between them?
  - **A:** `s01_column_ops.py` teaches *per-row, per-column* primitives — `.with_columns`, `.cast`, `.filter`, `.select`. These map cleanly to "change a value" or "drop a column". `s02_dedup_agg.py` teaches *group-level* operations — `.unique(subset=[...])`, `.group_by(...).agg(...)`, `.join`. These map to "collapse rows" and "combine tables". The arc is: master row-shape transforms first because they don't change the row count; then move to set-shape transforms which do. By the time the learner hits `06-full-etl/s02_silver_etl.py`, they recognize `unique → mask → filter → with_columns` as a composition of patterns they've each seen alone.
  - **Source:** `examples/02-polars-etl/s01_column_ops.py`, `examples/02-polars-etl/s02_dedup_agg.py`, `examples/06-full-etl/s02_silver_etl.py`

- **Q-019** [tag: knowhow, difficulty: hard]
  - **Q:** `02-polars-etl/s03_transform.py` uses `.map_elements(lambda v: hashlib.sha256(v.encode()).hexdigest(), return_dtype=pl.Utf8)` for PII masking. Why `map_elements` here instead of a native Polars expression? What's the cost?
  - **A:** `map_elements` calls the Python function row-by-row — that breaks Polars' Rust vectorization and is much slower than native expressions. The reason this script uses it is that SHA-256 doesn't have a native Polars expression; you have to drop into Python for the hash. The cost is that on a million-row Silver table this becomes a bottleneck — a senior version would either accept the cost (PII masking is rare-volume), batch the hashing via UDFs, or pre-compute hashes in an upstream system. The lesson worth quoting: "Polars stays in Rust until you escape it; `map_elements` is the escape hatch and the perf cliff."
  - **Source:** `examples/02-polars-etl/s03_transform.py`, `examples/06-full-etl/s02_silver_etl.py`

- **Q-020** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through the merge predicate in `03-merge-upsert/s01_basic_upsert.py`. Why is it a string, why is it aliased, and what would go wrong if you got the alias wrong?
  - **A:** The call is `DeltaTable(...).merge(source=df, predicate="target.id = source.id", source_alias="source", target_alias="target").when_matched_update_all().when_not_matched_insert_all().execute()`. Deltalake's Rust core parses the predicate as SQL — that's why it's a string, not a Python expression. The aliases tell the SQL parser which side of `target.id = source.id` refers to the existing table vs the incoming DataFrame. Mis-aliasing (e.g., `source.id = source.id`) would either silently match nothing (everything inserts) or, worse, match every row to itself (everything updates). The script convention of all-caps SQL keywords + lowercase aliases makes mistakes visually obvious.
  - **Source:** `examples/03-merge-upsert/s01_basic_upsert.py`, `examples/00-minimal-poc/s01_minimal_poc.py`

- **Q-021** [tag: knowhow, difficulty: hard]
  - **Q:** Why does `03-merge-upsert/` have two scripts (`s01_basic_upsert.py` with 2 rows, `s02_credit_profile.py` with 200 rows)? Same merge API in both — what's the point of the second one?
  - **A:** `s01_basic_upsert.py` teaches the mechanism (predicate, match clauses, execute). `s02_credit_profile.py` makes a *performance* point: merge only rewrites the Parquet files that contain matched or inserted rows, not the whole table. With 2 rows the cost difference is invisible; with 200 baseline + 50 merge you can inspect S3 and see that only a couple of Parquet files were rewritten, not the full 200-row file. This is the door into "why Delta beats full-table-rewrite Parquet for upserts" — a learner who only sees `s01` doesn't get the *why*.
  - **Source:** `examples/03-merge-upsert/s01_basic_upsert.py`, `examples/03-merge-upsert/s02_credit_profile.py`

- **Q-022** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through what time travel actually gives you. Why are there two separate scripts in `04-time-travel/` (`s01_version_read.py` and `s02_history.py`) instead of one combined demo?
  - **A:** `s01_version_read.py` shows the reader-side API — `pl.read_delta(uri, version=0, ...)` against multiple versions. `s02_history.py` shows the inspector-side API — `DeltaTable(uri, ...).history()` returns the commit log (version, timestamp, operation, parameters). These are two distinct skills: "give me the data as of version N" vs "tell me what happened on this table". A combined script would muddle them. Together they answer the audit question "what did the table look like at 9am yesterday, and who changed it?" — the fintech-shaped use case that motivated the project.
  - **Source:** `examples/04-time-travel/s01_version_read.py`, `examples/04-time-travel/s02_history.py`, `README.rst`

- **Q-023** [tag: knowhow, difficulty: hard]
  - **Q:** `05-vacuum-schema/s01_vacuum.py` calls `vacuum(retention_hours=0, enforce_retention_duration=False)`. Why both flags, why those values, and why would this be dangerous in production?
  - **A:** `retention_hours=0` says "delete everything older than 0 hours" — i.e. everything not in the current version. `enforce_retention_duration=False` tells deltalake "yes, I really mean it, override the safety check that normally blocks retention < 168h". The combination is demo-only: a learner sees Parquet files actually disappear from S3. In production this is catastrophic — any reader currently scanning an older version would get `FileNotFoundError` mid-read, and any time-travel query against a vacuumed version fails forever. Production uses the default 168h (7 days) so concurrent readers always have a safe window.
  - **Source:** `examples/05-vacuum-schema/s01_vacuum.py`, `docs/learn-this-project/03-elevation-roadmap.md#d-production-safety-for-merge-vacuum`

- **Q-024** [tag: knowhow, difficulty: medium]
  - **Q:** `05-vacuum-schema/s02_schema_evolution.py` adds a column to an existing table using `.write_delta(uri, schema_mode="merge", ...)`. Walk through what happens to the existing rows' values for the new column, and why that's safer than rewriting the table.
  - **A:** Deltalake sees the new column in the incoming DataFrame, detects it's not in the table schema, and (because `schema_mode="merge"`) updates the schema in `_delta_log/` to add the column. Existing Parquet files are *not* rewritten — the new column reads as `NULL` for old rows. The whole operation is a metadata change plus a small append, not a table rewrite. The alternative (full table rewrite with the new column) would require reading every row, writing every Parquet file, and breaking every concurrent reader during the rewrite window. Schema evolution is one of Delta's headline features for a reason.
  - **Source:** `examples/05-vacuum-schema/s02_schema_evolution.py`

- **Q-025** [tag: knowhow, difficulty: hard]
  - **Q:** `06-full-etl/data/batch_1.json` has 10 transactions including a deliberate duplicate `transaction_id` (TXN003). Why is the duplicate there? What would a learner miss if it weren't?
  - **A:** The duplicate is the *teaching point* for the Silver layer. `s02_silver_etl.py` calls `.unique(subset=["transaction_id"])` as the first step — without a duplicate in Bronze, that line would look like superstition. Real-world payment systems regularly emit duplicates (retries, reconciliation, double-submits); the lesson is that Bronze is intentionally raw and dedup belongs in Silver. The `batch_2.json` overlap (TXN002, TXN005 reappearing with updated amounts) sets up the next lesson: merge as the right way to refresh existing rows in Silver.
  - **Source:** `examples/06-full-etl/data/batch_1.json`, `examples/06-full-etl/data/batch_2.json`, `examples/06-full-etl/s02_silver_etl.py`, `examples/06-full-etl/s03_incremental.py`

- **Q-026** [tag: knowhow, difficulty: hard]
  - **Q:** Walk through what `06-full-etl/s03_incremental.py` actually composes. Which earlier modules show up in it, and why is this the capstone?
  - **A:** `s03_incremental.py` does, in order: (a) `pl.read_ndjson("batch_2.json")` then `.write_delta(mode="append", ...)` into Bronze — that's `01-delta-read-write/s02_append.py`; (b) re-run the full ETL transforms from `02-polars-etl/` (`.unique`, `.map_elements` SHA-256, `.filter`, `.with_columns`); (c) `DeltaTable(silver_uri).merge(...).when_matched_update_all().when_not_matched_insert_all().execute()` from `03-merge-upsert/`; (d) `pl.read_delta(silver_uri, version=0)` vs `version=1` from `04-time-travel/`. The capstone proves the modules compose. If a learner can read `s03_incremental.py` and explain every line as "that came from module N", they've absorbed the curriculum.
  - **Source:** `examples/06-full-etl/s03_incremental.py`, `examples/01-delta-read-write/s02_append.py`, `examples/02-polars-etl/`, `examples/03-merge-upsert/`, `examples/04-time-travel/`

- **Q-027** [tag: mech, difficulty: medium]
  - **Q:** What's the on-disk layout of a Delta table on S3? Walk through what you'd see if you ran `aws s3 ls --recursive s3://bucket/.../bronze/` after a couple of writes.
  - **A:** You'd see two kinds of files. Under the table prefix root: `part-00000-*.parquet`, `part-00001-*.parquet`, ... — the actual data files, one or more per write. Under `_delta_log/` (a subdirectory under the table prefix): `00000000000000000000.json`, `00000000000000000001.json`, etc. — one JSON commit per version, each describing which Parquet files were added or removed. The Parquet files alone are just unordered data; the `_delta_log/` JSONs are what give Delta its transaction log. Vacuum deletes Parquet files; the JSONs persist (they're the audit trail).
  - **Source:** `examples/04-time-travel/s02_history.py`, `examples/05-vacuum-schema/s01_vacuum.py`

## D. Conventions, design rationale, and cross-cutting

- **Q-028** [tag: convention, difficulty: easy]
  - **Q:** What do the variable-name prefixes `s3dir_`, `s3path_`, and `df_` mean in this codebase, and what would go wrong if a contributor stopped using them?
  - **A:** `s3dir_` is an `S3Path` that points to a directory (with trailing slash semantics); `s3path_` is an `S3Path` that points to a single file; `df_` is a Polars DataFrame. The prefixes substitute for type hints — at a glance you know whether to call `.iterdir()` (s3dir) or `.read_text()` (s3path), and whether a variable is in-memory or remote. Drop the convention and you'd see calls like `data.write_delta(...)` and have to read several lines to know if `data` is a DataFrame or an S3 URI string. The convention also makes copy-paste between scripts safer.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py`, `docs/learn-this-project/01-knowhow-inventory.md#conventions`

- **Q-029** [tag: convention, difficulty: medium]
  - **Q:** Why does the project use a `sNN_xxx.py` numeric prefix convention in `examples/` (and `one_NN_xxx.py` in the `one/` package)? Why not rely on `README.md` to order things?
  - **A:** The numeric prefix means a learner's `ls examples/01-delta-read-write/` shows the scripts in pedagogical order — no need to read prose to figure out which to open first. IDEs (PyCharm, VSCode) sort the file tree the same way. README files are useful but they're a second source of truth that can drift from filesystem reality. Same logic inside `one/`: `one_01_main.py` is the entry point, `one_02_config.py`, `one_03_boto_ses.py`, `one_04_s3.py` are progressively layered capabilities. Anyone scanning the directory sees the layering at the file level.
  - **Source:** `examples/`, `delta_lake_and_polars_basic/one/`

- **Q-030** [tag: convention, difficulty: medium]
  - **Q:** The `.write_delta(...)` calls in this project are always written multi-line, with `mode=` and `storage_options=` on their own lines, even when they'd fit on one. Why?
  - **A:** `.write_delta(...)` is the single most-modified call in any given script — learners adjust the mode (`overwrite` → `append` → `error`), tweak storage options, add `schema_mode="merge"` later. Putting each kwarg on its own line means diffs are line-additions, not within-line changes, which makes code review and `git blame` much cleaner. It also matches the project's "the lesson is in the kwargs" pedagogy — visual prominence aids learning. A one-liner would compress the same information but obscure what changed between two scripts.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py`, `examples/01-delta-read-write/s01_overwrite.py`, `examples/05-vacuum-schema/s02_schema_evolution.py`

- **Q-031** [tag: knowhow, difficulty: hard]
  - **Q:** The project chose `polars + deltalake` (Rust-native) over `PySpark + Delta`. What's the tradeoff, and where would that decision become wrong?
  - **A:** Polars + deltalake runs entirely in-process, no JVM, no cluster — fits inside an AWS Lambda's 15-minute / 10GB envelope. The fintech context is "single-machine batch ETL on GB-scale data". PySpark's overhead (JVM warmup, cluster provisioning) wins only at TB-scale or for workloads needing distributed shuffles. Where this choice becomes wrong: when a single Bronze table exceeds RAM (~100 GB), when joins need cross-machine shuffle, when you need Spark Streaming's mature event-time/watermark semantics, or when your team already runs Spark for other reasons (operational cost of a second stack). The project is explicit about its scope; production beyond ~100 GB working set should re-evaluate.
  - **Source:** `README.rst`, `docs/learn-this-project/01-knowhow-inventory.md#external-dependencies`

- **Q-032** [tag: knowhow, difficulty: medium]
  - **Q:** Why does the project use `s3pathlib` to manipulate S3 paths instead of raw `boto3` `s3_client.put_object(Bucket=..., Key=...)` calls?
  - **A:** `s3pathlib.S3Path` lets you chain operations the way `pathlib` does — `s3dir_root.joinpath("bronze").to_dir()` instead of `f"s3://{bucket}/{prefix}/bronze/"` string templating. Fewer trailing-slash bugs, fewer accidentally-empty path segments, and methods like `.delete(bsm=bsm)` or `.iterdir(bsm=bsm)` work directly on the path. Raw boto3 is still available via `one.boto_ses` for the cases s3pathlib doesn't cover. The cost is one more dependency to learn; the gain is removing a class of stringly-typed S3 bugs that show up only at runtime.
  - **Source:** `delta_lake_and_polars_basic/one/one_04_s3.py`, `examples/01-delta-read-write/s01_overwrite.py`

- **Q-033** [tag: knowhow, difficulty: medium]
  - **Q:** `mise.toml` declares `[env] _.file = ".env"`. What does this actually do, and what's the consequence if a contributor uses `.env.local` instead?
  - **A:** That declaration tells mise: every time a `mise run <task>` command runs, source the `.env` file into the environment first. So `AWS_PROFILE` set in `.env` becomes available to every Python subprocess mise spawns. A contributor who names the file `.env.local` instead of `.env` will have a green `mise install` and a green `mise run inst`, but `python examples/01-delta-read-write/s01_overwrite.py` will fail at module load with `KeyError: 'AWS_PROFILE'` — and the failure won't point at the naming issue. This is the #1 setup footgun and is called out in the runbook.
  - **Source:** `mise.toml`, `docs/learn-this-project/02-runbook.md#common-failures-and-fixes`

- **Q-034** [tag: knowhow, difficulty: hard]
  - **Q:** `vendor/pytest_cov_helper.py` lives under a `vendor/` subdirectory. What does the `vendor/` naming convention typically signal, and would you expect this helper to be the project's own code or borrowed?
  - **A:** `vendor/` by convention holds code copied or borrowed from elsewhere — third-party snippets the project chose to bundle rather than depend on as a pip package. The expectation is that this helper is a small utility the author maintains across multiple projects and copies in rather than publishing as a library. The advantage is no external dep + zero risk of upstream API change; the cost is no central place to fix bugs (every copy diverges). For a tiny helper like this (~60 lines), vendoring is the right call — packaging it would be more friction than the borrowing is worth.
  - **Source:** `delta_lake_and_polars_basic/vendor/pytest_cov_helper.py`, `delta_lake_and_polars_basic/tests/helper.py`

- **Q-035** [tag: knowhow, difficulty: hard]
  - **Q:** The project has zero actual test files (only `tests/helper.py`). But `mise run test` and `mise run cov` exist and pass. Walk through why this state exists and what it tells you about the author's priorities.
  - **A:** The test plumbing (`tests/helper.py`, `vendor/pytest_cov_helper.py`, `mise.toml` tasks) is scaffolded — ready to receive test files but not populated. `mise run test` runs `pytest tests` which collects zero tests and exits 0 (vacuously green). This pattern says: the author built the infrastructure first because adding it later is friction-heavy, but treated the *content* of tests as a separate (still-pending) workstream. For a learning-focused repo, this is a defensible tradeoff — the examples themselves serve as integration tests when run manually. The elevation roadmap calls this out as the highest-leverage upgrade.
  - **Source:** `delta_lake_and_polars_basic/tests/`, `vendor/pytest_cov_helper.py`, `mise.toml`, `docs/learn-this-project/03-elevation-roadmap.md#a-test-depth-and-coverage`

## E. Series questions — cross-style and cross-module comparisons

- **Q-036** [tag: series, difficulty: hard]
  - **Q:** Across the four S3-touching scripts that write data (`s01_overwrite.py`, `s02_append.py`, the merge scripts, `06-full-etl/s01_bronze_write.py`), each uses `mode=` differently. Walk through which mode each chose and why a single mode wouldn't have worked across all four.
  - **A:** `01-delta-read-write/s01_overwrite.py` uses `mode="overwrite"` — the lesson is "wipe and replace". `s02_append.py` uses `mode="append"` — the lesson is "add without dedup". `03-merge-upsert/s01_basic_upsert.py` uses `DeltaTable.merge(...)` rather than `mode=` at all — merge is its own API because it needs predicates. `06-full-etl/s01_bronze_write.py` uses `mode="overwrite"` because Bronze is a fresh ingest from a JSON file (idempotent re-ingest of the same batch). The point of the spread: the right mode depends on the *semantic intent*, not the mechanical operation. The mode argument forces you to be explicit about intent every time.
  - **Source:** `examples/01-delta-read-write/`, `examples/03-merge-upsert/s01_basic_upsert.py`, `examples/06-full-etl/s01_bronze_write.py`

- **Q-037** [tag: series, difficulty: hard]
  - **Q:** Compare how `06-full-etl/s02_silver_etl.py` and `02-polars-etl/` differ in style. Same transforms — what changed and why?
  - **A:** `02-polars-etl/` scripts construct `pl.DataFrame(...)` from literal Python dicts and stop after `print(df)`. `s02_silver_etl.py` reads from S3 (`pl.read_delta(bronze_uri, storage_options=...)`), runs the same `.unique` / `.map_elements` / `.filter` / `.with_columns` chain, then writes back to S3 (`.write_delta(silver_uri, mode="overwrite", ...)`). The transforms are identical; the I/O bookends are what changed. The split is deliberate: the polars-etl module isolates the transformation lessons; the full-etl module shows the same lessons composed into a real ingest→transform→write pipeline. A learner who tries to combine I/O + transforms on day one gets confused about which bug is in which half.
  - **Source:** `examples/02-polars-etl/`, `examples/06-full-etl/s02_silver_etl.py`

- **Q-038** [tag: series, difficulty: hard]
  - **Q:** Where does the project's "demo mode" leak through, and where is it intentional? Walk through 2–3 examples and explain why each is a deliberate teaching simplification.
  - **A:** Three big tells: (1) `AWS_S3_ALLOW_UNSAFE_RENAME="true"` in `one/one_03_boto_ses.py` — skips DynamoDB locking, fine for one writer, dangerous in prod. (2) `vacuum(retention_hours=0, enforce_retention_duration=False)` in `05-vacuum-schema/s01_vacuum.py` — production would use 168+ hours. (3) Bare `print()` statements throughout — production would use structured logging. Each is a deliberate simplification that lets the lesson land without operational scaffolding; each is also called out in the elevation roadmap as a "make this explicitly switchable" upgrade. The pattern itself is the lesson: production-ready means making the demo-vs-prod choice *visible and explicit*, not hiding it behind a default.
  - **Source:** `delta_lake_and_polars_basic/one/one_03_boto_ses.py`, `examples/05-vacuum-schema/s01_vacuum.py`, `docs/learn-this-project/03-elevation-roadmap.md`
