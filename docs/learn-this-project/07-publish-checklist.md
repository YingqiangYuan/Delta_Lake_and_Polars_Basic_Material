## 4. README co-write outline — English, D-mode

This is the structure the publish skill follows in Transform mode's D-style co-write (user provides the content; skill drafts from user's words). The skill asks each question, waits for the user's answer, then drafts that section in prose.

### Section: Project description

**Goal:** Communicate in one sentence what this project is and why someone should care.

**Question prompts:**
1. "In one sentence, what is this project?"
2. "Who would care about it and why?"
3. "What's the simplest way to describe what it teaches?"

**Length target:** 50–80 words

---

### Section: Install & run

**Goal:** Give the minimum command sequence from clone to working output.

**Question prompts:**
1. "What's the first command someone runs after cloning?"
2. "What do they need to set up (env vars, AWS profile, etc.)?"
3. "What command proves the setup worked?"

**Length target:** 50–100 words

---

### Section: What I learned

**Goal:** Reflect on the experience. What surprised you? What was hard? What's the payoff?

**Question prompts:**
1. "What surprised you most about Delta Lake or Polars?"
2. "If a friend asked 'what was the point?', what would you say?"
3. "What was the hardest part to understand?"

**Length target:** 80–120 words

---

### Section: What's next (optional)

**Goal:** Leave the reader with a sense of where the project could go.

**Question prompts:**
1. "If you spent another week on this, what would you add?"
2. "What production concerns are missing from the POC?"

**Length target:** 50–80 words (or omit if not relevant)

---

**Total README target:** 250–500 words, English only, first-person past tense for what was done, present tense for what the project is.

## 5. Hostile-scan rules for Audit mode

The publish skill's Audit mode scans the repo with the question "did this come from a tutorial?" These are the detection patterns grouped by severity.

### 🔴 HIGH RISK — fatal on detection

| Rule category | Detection pattern | Fix |
|---|---|---|
| **File-pattern flags** | `README-cn.md`, `TICKET.md` — any non-root README or `.md` files signaling course origin | Delete file; verify no other teaching READMEs exist |
| **File-pattern flags** | Directory `docs/learn-this-project/` or `docs/tutorials/` anywhere | Delete entire directory; verify no `docs/learn-*/` or `docs/tutorials/` remain |
| **File-pattern flags** | Directory `.claude/skills/learn-this-project-{absorb,elevate,quiz,interview,demo,publish}/` | Delete each directory; keep only `learn-this-project-meta/` (portfolio bonus) |
| **README phrase flags** | In `README.md`: "this tutorial", "in this course", "this lesson", "we learned", "mentor", "as a student", "learning objective" | Reword to hide teaching origin (e.g. "I built this to..." instead of "we learned...") |
| **Commit message phrase flags** | In commit subjects/bodies: "tutorial", "course", "lesson", "teaching", "mentor", "add course material" | Rebase and reword commits; or accept if history is immutable |
| **Git ref flags** | Tags or branches named `tutorial-*`, `v0-from-course`, `original`, `from-tutorial`, `lesson-*` | Delete the tag or branch |
| **Residual directory flags** | Any `.claude/skills/learn-this-project-*/` directory OTHER than `meta/` | Delete the directory; verify none remain except `meta/` |

### 🟡 MEDIUM RISK — recoverable but visible

| Rule category | Detection pattern | Fix |
|---|---|---|
| **Commit message phrase flags** | Commits with tone like "add lesson X", "implement example", templated messages suggesting batch generation | Optional: rebase and reword for human voice. Or accept — it's less damning than HIGH RISK |
| **Suspicious symmetry flags** | Multiple source files with identical 10+ line comment banners or docstring boilerplate across the codebase | Optional: vary the banner or remove boilerplate. Or accept — signals efficiency, not necessarily tutorial origin |
| **File-pattern flags** | `.venv/`, `__pycache__/`, `.pyc`, `*.egg-info/` still committed | Add to `.gitignore` and `git rm --cached`; run locally before push |

### 🔵 LOW RISK — cosmetic

| Rule category | Detection pattern | Fix |
|---|---|---|
| **Hygiene flags** | `.DS_Store`, `.idea/`, `.vscode/` committed | Add to `.gitignore` and `git rm --cached` |
| **Hygiene flags** | Missing `.gitignore` entries for Python (venv, __pycache__, .egg-info) | Create or extend `.gitignore` |

## Audit report format

When the publish skill runs Audit mode, it produces a structured report:

```
🔴 HIGH RISK (N findings)
- <finding 1>: <path> → <suggested fix>
- <finding 2>: <path> → <suggested fix>

🟡 MEDIUM RISK (N findings)
- <finding 1>: <path> → <suggested fix>

🔵 LOW RISK (N findings)
- <finding 1>: <path> → <suggested fix>
```

If zero 🔴 findings remain, the repo passes hostile-scan and is safe to publish. If any 🔴 findings remain, Transform is incomplete — the skill will refuse to finalize and ask the user to fix them.

## Notes for edge cases

- If the README is very long and naturally spans 500+ words after co-write, that's okay — aim for prose clarity over word count.
- If the user has already rewritten `README.md` before running publish, the skill detects this (by comparing against a known teaching version) and skips the co-write.
- If the user chooses to keep borderline items (e.g., `.idea/`), they'll show up as 🔵 LOW RISK findings in Audit but won't block publication.
- If commit history is immutable (e.g., merged to a shared branch), accept MEDIUM RISK commit messages as-is — the skill can't rewrite history without user consent.
