# 06 — Demo Playbook

## Wow features

### 1. Full Bronze-to-Silver ETL pipeline with incremental merge (strongest)
**What:** `examples/06-full-etl/` — a complete incremental data pipeline: raw JSON → Bronze (append) → Silver (dedup + PII mask + filter + merge). Second batch updates existing rows and inserts new ones, verified via time travel.
**Why it lands:** Shows real-world data engineering: PII handling, dedup, incremental processing, and audit trail — all in ~100 lines of Python with no Spark.
**File to open:** `examples/06-full-etl/s03_incremental.py`

### 2. Delta Lake merge/upsert at scale
**What:** `examples/03-merge-upsert/s02_credit_profile.py` — 200-row baseline + 50-row merge with assertion-based verification.
**Why it lands:** The merge is the killer feature of Delta Lake. Showing it with verification (row counts, specific field updates) demonstrates production-grade thinking.
**File to open:** `examples/03-merge-upsert/s02_credit_profile.py`

### 3. Time travel and audit
**What:** `examples/04-time-travel/` — read any historical version, inspect the commit log.
**Why it lands:** "You can read what this table looked like 3 versions ago" is a concrete, memorable feature that non-engineers understand too.
**File to open:** `examples/04-time-travel/s01_version_read.py`

## Recommended sequence — 5-minute version

1. **Open** `examples/README.md`. Say: "This is a learning project for Delta Lake and Polars — the Spark-free data lake stack. Seven progressive modules, each isolating one concept."
2. **Jump to** `examples/06-full-etl/s02_silver_etl.py`. Say: "This is the heart — a Bronze-to-Silver ETL. Raw JSON comes in, gets deduplicated, PII is masked with SHA-256, declined transactions are filtered, and the result writes to a Delta table on S3."
3. **Scroll to** the transform chain (the `with_columns` + `filter` block). Say: "Four transformations, one pipeline. Polars makes this readable."
4. **Open** `examples/06-full-etl/s03_incremental.py`. Say: "Then the incremental run: a second batch arrives, gets the same ETL, and merges into Silver. Existing rows update, new rows insert — atomically. I verify with time travel."
5. **Close** with: "No Spark, no JVM. Python calling Rust libraries. Every script is idempotent and uses mock data — you can clone and run it in 5 minutes."

## Recommended sequence — 15-minute version

1. **Open** `examples/README.md`. (1 min) Give the 7-module overview. Mention the progression: basic I/O → transforms → merge → time travel → maintenance → full pipeline.
2. **Run** `examples/00-minimal-poc/s01_minimal_poc.py` live (if AWS is configured). (2 min) Say: "This is the golden reference — creates data, writes to S3, reads it back, upserts. Sixty lines, complete cycle." Show the S3 console URL output.
3. **Open** `examples/02-polars-etl/s03_transform.py`. (2 min) Walk through the PII masking pattern — SHA-256 hash, `when/then/otherwise`, chained `with_columns`. Say: "This is the template that scales to the full ETL."
4. **Open** `examples/03-merge-upsert/s02_credit_profile.py`. (2 min) Say: "200 customers, 50-row merge — 30 updates, 20 inserts. Watch the assertions." Run it if live.
5. **Open** `examples/04-time-travel/s01_version_read.py`. (2 min) Say: "Every write creates a version. Read version 0, version 1, version 2 — full audit trail."
6. **Walk through** `examples/06-full-etl/` end-to-end. (4 min) Say: "Bronze loads raw. Silver cleans. Incremental run merges. Time travel verifies. This mirrors the production pipeline I built."
7. **Close** (2 min) with architecture reflection: "Stack is Polars + delta-rs on S3. No Spark. Idempotent scripts. Mock data. Production patterns extracted into learnable units."

## Recovery moves

| Beat fails... | Say this |
|---|---|
| AWS credentials not working (scripts fail) | "Let me show the code statically — it's self-explanatory. Here's the input data, here's the transform chain, and here's what the output looks like." Open `data/batch_1.json` and walk through the ETL logic on paper. |
| S3 is slow or times out | "S3 can be latent. While that runs, let me walk you through the Delta transaction log concept..." Switch to `04-time-travel/s02_history.py` and explain the commit log. |
| `02-polars-etl` scripts error | These have no S3 dependency. Check: is the venv activated? Is Polars installed? Fix with `mise run inst`. |
| Merge shows unexpected row counts | "Interesting — let me debug in real time." Use time travel to read the pre-merge state and compare. This actually makes a great demo moment. |
| Can't remember the script order for 06-full-etl | "It's s01 Bronze write, s02 Silver ETL, s03 incremental merge." Or just open `examples/README.md`. |

## Rehearsal questions

1. **"Why not just use Spark?"** — Lead with: "delta-rs gives you Delta Lake features without JVM overhead. For container/Lambda workloads or single-machine ETL, it's the right tool."

2. **"How does this handle real production data volumes?"** — Lead with: "The patterns scale — Polars handles millions of rows in-memory, and Delta Lake's merge is partition-aware. The main bottleneck in this POC is the full-recompute Silver ETL, which I'd replace with CDC in production."

3. **"What was the hardest part of building this?"** — Lead with: "Getting the credential injection right. Polars and deltalake need AWS credentials passed as a dict, not via the default credential chain. The `one` singleton solves this, but debugging STS token expiration was tricky."

4. **"Why are there 7 modules? Why not just the full ETL?"** — Lead with: "Pedagogical progression. Each module isolates one concept so you can understand it before combining. The full ETL is the payoff — but if you don't understand merge, time travel, and schema evolution individually, the pipeline is a black box."

5. **"Can I clone this and run it?"** — Lead with: "Yes. `mise run inst`, set your AWS profile in `.env`, and run any script. They're idempotent — delete and rebuild every time. No real data involved."
