# 06 — Demo Playbook

How to demo **delta_lake_and_polars_basic** effectively — pick the right entry point, sequence the wow, hide the messy parts, tailor to the audience. The `/learn-this-project-demo` skill consumes this doc.

## Cardinal precondition — demo from a sanitized fork

Before any rehearsal: **demo the published, hostile-scanned version of this repo, not this one.** This repo is the teaching version — it contains `README-cn.md`, `TICKET.md`, `docs/learn-this-project/`, and `.claude/skills/learn-this-project-*` siblings. A hiring manager who sees those concludes "this is a tutorial repo", and the demo's signal flips from "this person learned a hard thing" to "this person ran a tutorial". Run `/learn-this-project-publish` first; demo from the sanitized fork.

If the user insists on demoing this repo as-is, the skill must surface the risk explicitly and decline to endorse the demo script.

## 1. Wow features (in priority order)

The three things in this project that most reliably land:

### Wow #1 — Time travel + commit log (the audit story)

- **What:** Open `examples/04-time-travel/s02_history.py`. Run it. Show the output: a list of commits with version, timestamp, operation (`WRITE`, `MERGE`, `VACUUM`), and `operationParameters`. Then open `s01_version_read.py` and show the same table at version 0, version 1, and latest.
- **Why it lands:** Most engineers have never seen a database that lets you query "what did this table look like at 9am yesterday" without managing backups. The commit-log view answers "who changed what and when" without setting up CloudTrail. For fintech audiences this is the single highest-signal feature.
- **Open:** `examples/04-time-travel/s02_history.py`

### Wow #2 — Incremental merge (the upsert story)

- **What:** Open `examples/06-full-etl/s03_incremental.py`. Walk through what it does: appends `batch_2.json` to Bronze, re-runs ETL on the new data, *merges* the result into Silver (not overwrite), then time-travels to compare Silver v0 vs v1. Run it. Inspect S3 (or `DeltaTable.history()`) afterwards to confirm only a handful of Parquet files were rewritten.
- **Why it lands:** Upsert is the single most-asked-for feature in data lakes. Showing it work end-to-end (with the audit step at the end) demonstrates the merge story isn't just an API — it's a workflow.
- **Open:** `examples/06-full-etl/s03_incremental.py`

### Wow #3 — Schema evolution without a rewrite

- **What:** Open `examples/05-vacuum-schema/s02_schema_evolution.py`. Run it. Show that an existing table gained a new column without a full rewrite — old rows show NULL for the new column, new rows have values.
- **Why it lands:** Anyone who has done a schema migration on a real production database has scars. "I added a column and didn't rewrite the table" is a credibility moment for a fintech-shaped audience.
- **Open:** `examples/05-vacuum-schema/s02_schema_evolution.py`

## 2. Recommended sequences

### 2a. 5-minute demo (golden path)

1. **0:00 — Frame the project (15 sec).** "Built this to deeply understand Delta Lake and Polars on S3 — the patterns my team's fintech data lake relies on, without Spark."
2. **0:15 — Open `examples/README.md` (15 sec).** Scroll to show the 7-module structure. Say: "Seven progressive modules, 16 scripts, each isolates one concept."
3. **0:30 — Open `examples/04-time-travel/s02_history.py` (90 sec).** Run it. Walk through the output — version, timestamp, operation. Say: "Every write creates an immutable version. This is the audit trail for free."
4. **2:00 — Switch to `examples/06-full-etl/s03_incremental.py` (2 min).** Walk through the script structure: "this appends to Bronze, re-runs ETL, merges into Silver, then time-travels Silver to compare v0 vs v1." Run it. Show the row counts.
5. **4:00 — Close (1 min).** "The non-obvious design choice is going Rust-native instead of Spark — fits in Lambda, sub-second startup, same Delta format Spark could read tomorrow. I documented the elevation roadmap separately if you'd like to see what I'd add with another 3 months."

### 2b. 15-minute walkthrough

Builds on the 5-minute version:

1. **0:00–2:00 — Pitch + structure (same as 5-min).**
2. **2:00–4:00 — `examples/02-polars-etl/s01_column_ops.py`.** Walk through Polars primitives. Tee up: "this module deliberately avoids S3 — Polars in isolation first."
3. **4:00–6:00 — `examples/01-delta-read-write/s02_append.py`.** Run it. Show that append doesn't dedup. Use this as the bridge: "which is why module 03 introduces merge."
4. **6:00–9:00 — `examples/03-merge-upsert/s02_credit_profile.py`.** Walk through the merge predicate. Run it. If time, show `DeltaTable.history()` to highlight the operation parameters.
5. **9:00–12:00 — `examples/04-time-travel/s02_history.py` + `s01_version_read.py`.** Same as the 5-min, but with the merge from step 4 as the most recent commit.
6. **12:00–14:00 — `examples/06-full-etl/s03_incremental.py`.** The capstone — walk through how it composes everything seen so far.
7. **14:00–15:00 — Architecture + close.** Open `delta_lake_and_polars_basic/one/one_01_main.py`. Show the mixin composition. Close with the Polars-vs-Spark tradeoff and the elevation roadmap.

## 5. Recovery moves — what to say if a beat fails live

| If this fails | Say this | Fallback |
|---|---|---|
| `examples/06-full-etl/s03_incremental.py` errors on the merge | "Looks like there's state from a previous run — let me clean it." Run `s3dir.delete(bsm=bsm)` then re-run. | If still fails, switch to `s02_silver_etl.py` (the non-merge ETL) and explain merge from the script text alone. |
| `DeltaTable.history()` returns empty / fails | "Looks like the table doesn't exist on S3 — let me re-run the write." Re-run the previous beat to seed it. | If S3 access itself broken, switch to walking the code without execution; lean on `06-full-etl/s03_incremental.py`'s structure to tell the story. |
| `pl.read_delta(...)` returns zero rows | "S3 consistency lag — give it a second." Wait 5 seconds, re-run. | If persistent, show `DeltaTable.history()` to prove the commit landed; describe the data verbally. |
| AWS credentials expired mid-demo | "Sessions expired — back in 30 seconds." Run your refresh command. | Don't try to demo more S3 beats; switch to `examples/02-polars-etl/` for a pure-local close. |
| Anything else fails in a way that can't recover in <60 sec | "Real life. Let me walk you through the code instead." Open the file, talk through the structure. | Always have a non-runnable backup: the architecture talk (`one_01_main.py` + mixin walkthrough) works with zero infrastructure. |

## 6. Rehearsal questions (what a viewer might ask)

Use these in `/learn-this-project-demo` Rehearsal mode. Each is followed by a one-line hint at the strong answer.

1. **"Why Polars + deltalake instead of PySpark?"** → JVM/cluster overhead vs Lambda envelope; Polars wins at single-machine GB scale; same Delta format means a Spark consumer could read these tables tomorrow.
2. **"How is this safe for multiple writers in production?"** → It's not as-is — `AWS_S3_ALLOW_UNSAFE_RENAME=true` is a demo flag. Production needs the DynamoDB lock table; the elevation roadmap §D maps the upgrade.
3. **"What's the difference between merge and append?"** → Append adds rows unconditionally (no dedup); merge takes a predicate and update/insert clauses. Show `s02_append.py` then `s01_basic_upsert.py` side by side.
4. **"Where do I find what your `one` singleton actually does?"** → `delta_lake_and_polars_basic/one/one_01_main.py` composes three mixins. Walk through it briefly.
5. **"What would you do with another 3 months on this?"** → Tests first (plumbing is in, content is missing), then CI, then surface the demo-vs-prod boundary explicitly. Point at `docs/learn-this-project/03-elevation-roadmap.md` for the full list.
