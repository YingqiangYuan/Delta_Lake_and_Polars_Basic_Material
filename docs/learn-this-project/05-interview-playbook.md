# 05 — Interview Playbook

Production-grade interviewer questions for the **delta_lake_and_polars_basic** project, with model answers (reference for the skill — never read to the candidate). Five rounds, calibrated by the `/learn-this-project-interview` skill's intake.

## Opening — the 90-second pitch (model script)

> "This is a 16-script proof-of-concept I built to deeply understand Delta Lake and Polars on S3 — specifically the patterns my team's production fintech data lake relies on: incremental upserts, schema evolution, audit-friendly time travel, all without Spark. The project is organized into seven progressive modules in `examples/`: Polars in isolation, basic Delta read/write, merge/upsert, time travel, vacuum and schema evolution, and a capstone Bronze→Silver pipeline. A thin core package centralizes AWS credential management through a singleton `one` object built with mixin composition, so all 16 example scripts share the same auth and S3 path resolution. The technology choice — Polars + deltalake Rust libraries instead of PySpark — is deliberate: it fits inside an AWS Lambda's 15-minute envelope and avoids JVM operational overhead, which matches the team's serverless-first architecture. I'd be happy to walk through any of these in depth."

## Round 1 — What you have (architecture, mechanism, data flow)

### Q1.1 — Walk me through what happens when you run `examples/06-full-etl/s03_incremental.py`.

- **Model answer:** The script orchestrates a full incremental flow. First it reads `data/batch_2.json` with `pl.read_ndjson()`, then appends those 5 rows to the Bronze Delta table using `mode="append"`. Then it reads the Bronze table back, applies the same Silver transforms — `unique(subset=["transaction_id"])` for dedup, SHA-256 mask on `card_id`, `filter` out DECLINED, add `etl_ts` — and *merges* the result into the Silver table using `DeltaTable.merge(...)` with the standard `when_matched_update_all().when_not_matched_insert_all()` clauses. Finally it reads Silver at version 0 and version 1 and compares the row counts to prove the audit-trail story works.
- **Follow-ups:** "Why use merge instead of overwrite on Silver?" / "How does Delta know which Parquet files to rewrite?" / "What happens if the merge sees a row that matches but with NULL key — does it match or skip?"
- **Weak answer signature:** Just lists the script's steps in order without explaining the merge semantics or the time-travel audit step.

### Q1.2 — Explain the singleton `one` and why this project chose a mixin pattern for it.

- **Model answer:** `one` is a single instance of class `One`, defined in `delta_lake_and_polars_basic/one/one_01_main.py` as `class One(OneConfigMixin, OneBotoSesMixin, OneS3Mixin): pass`. Each mixin lives in its own ~30-line file and adds one capability — `OneBotoSesMixin` provides the boto3 session and the frozen-credential dict that Polars needs, `OneS3Mixin` derives the bucket name from the AWS account alias and exposes `s3dir_root`. Routing all AWS access through this singleton means a learner sets `AWS_PROFILE` once in `.env` and never re-types boto3 setup across 16 scripts. The mixin shape (rather than monolithic class) makes adding a new capability — say, a Glue Catalog mixin — a one-file change, and lets each mixin be tested independently.
- **Follow-ups:** "What's `polars_storage_options` doing that bare boto3 wouldn't?" / "What happens if two scripts import `one` at the same time?" / "Could you do this with dependency injection instead?"
- **Weak answer:** "It's a config object" — no mention of mixins, no explanation of *why* singleton vs DI.

### Q1.3 — How does Delta Lake store data on S3? What does the on-disk layout actually look like?

- **Model answer:** Each Delta table is an S3 prefix containing two things: `part-NNNNN-*.parquet` data files at the prefix root, and a `_delta_log/` subdirectory with sequential JSON files (`00000000000000000000.json`, `00000000000000000001.json`, …). Each JSON commit describes which Parquet files were added or removed in that version. Parquet files themselves are immutable; mutations happen by writing new Parquet files and a new commit JSON that supersedes the previous one. Vacuum cleans up the orphaned Parquet files; the `_delta_log/` is the authoritative source of truth for "what's in this table right now and at any past version".
- **Follow-ups:** "What happens to old `_delta_log/` files — are they ever vacuumed?" (answer: no, retained forever by default — that's how time travel survives vacuum) / "What if two writers commit at the same version number?" (answer: that's what the DynamoDB lock prevents — this project skips it via `ALLOW_UNSAFE_RENAME=true`).
- **Weak answer:** "It's Parquet files with metadata" — no description of the `_delta_log/` JSON structure or commit numbering.

### Q1.4 — Why does `02-polars-etl/` deliberately avoid S3 while the rest of the curriculum embraces it?

- **Model answer:** It's a pedagogical separation. The three scripts in `02-polars-etl/` — `s01_column_ops.py`, `s02_dedup_agg.py`, `s03_transform.py` — never import `one` and never call `pl.read_delta` or `pl.DataFrame.write_delta`. They isolate the Polars DataFrame API so a learner builds Polars fluency before adding S3/Delta complexity. The benefit shows up when something later breaks: the learner can localize the bug to the Polars half or the Delta half instead of debugging the whole stack. As a side benefit, `02-polars-etl/` becomes a viable "first day, no AWS access yet" on-ramp.
- **Follow-ups:** "If you were redesigning, would you keep that separation or merge it in?" / "What other modules in this curriculum could be similarly stripped?"
- **Weak answer:** "It teaches Polars" — without naming the separation rationale.

### Q1.5 — Walk through the merge predicate pattern. What's the SQL doing, and what would go wrong if you mis-aliased?

- **Model answer:** The call shape is `DeltaTable(uri, ...).merge(source=df, predicate="target.id = source.id", source_alias="source", target_alias="target").when_matched_update_all().when_not_matched_insert_all().execute()` — see `examples/03-merge-upsert/s01_basic_upsert.py`. The predicate is a SQL string parsed by deltalake's Rust core, not a Python expression. The aliases tell the parser which side is the existing table vs the incoming DataFrame. Mis-aliasing (e.g., `source.id = source.id`) would either silently match nothing (everything inserts as new rows, doubling the table) or match every row to itself (every row updates with itself, no-op but expensive). The all-caps SQL keywords convention plus the lowercase aliases is what makes the predicate readable.
- **Follow-ups:** "What if your match key contains NULL?" / "What does `when_matched_update_all()` actually do under the hood — full Parquet rewrite?"
- **Weak answer:** Quotes the API but doesn't articulate the alias trap.

## Round 2 — What you'd elevate (3–6 months of investment)

### Q2.1 — If I gave you three months on this project, what's the highest-leverage thing you'd add?

- **Model answer:** Tests for the example scripts. The plumbing is fully there — `vendor/pytest_cov_helper.py`, `tests/helper.py`, `mise run cov` — but there are zero actual test files. The lowest-friction first iteration is `tests/test_examples.py` that subprocess-runs each script and asserts exit code 0 + presence of one expected ASCII marker in stdout. That's a half-day of work and catches every regression from a `polars` or `deltalake` version bump. Once that exists, layering CI on top is straightforward and unlocks every subsequent upgrade.
- **Follow-ups:** "Why not start with type hints / lint?" / "Would you use moto for the S3-touching scripts or test against a real account?" / "How would you measure that the tests are doing their job?"
- **Weak answer:** Picks something showy (e.g., a streaming module) without acknowledging the test gap.

### Q2.2 — The project skips DynamoDB locking via `AWS_S3_ALLOW_UNSAFE_RENAME=true`. How would you make this safe for a multi-writer production deployment?

- **Model answer:** Two things. First, refactor `one.polars_storage_options` into two flavors — `polars_storage_options_demo` (current behavior) and `polars_storage_options_prod` (DynamoDB lock table specified, no unsafe-rename flag). Even better, require an explicit `mode="demo" | "prod"` argument to `One()` so demo defaults can't be silently inherited in production code. Second, provision a DynamoDB lock table with the schema deltalake expects, configure its name via env variable, and add an integration test that runs two `merge` operations concurrently to verify the lock actually fires. Both changes are called out in the elevation roadmap.
- **Follow-ups:** "What's the failure mode if two writers do commit at the same version?" / "How does the DynamoDB schema look — what's the partition key?" / "Could you use S3 conditional writes instead, now that S3 has them?"
- **Weak answer:** "Add DynamoDB locking" without explaining how the demo-vs-prod boundary becomes explicit.

### Q2.3 — How would you add observability so a learner can compare merge vs overwrite empirically?

- **Model answer:** Pick `loguru` for low-config structured logging, add it to the `dev` extra. Wrap each script's top-level work in a context manager that emits a structured record `{op: "write_delta", mode: "overwrite", n_rows: 1000, duration_ms: 312, n_files_written: 3}`. Update one or two examples — `00-minimal-poc/s01_minimal_poc.py` is a good reference — and let the rest follow as the curriculum is touched. The win is concrete: the learner can run `s02_credit_profile.py` and see "merge rewrote 3 Parquet files, 312 ms" vs a full overwrite "rewrote 12 Parquet files, 1140 ms" — that's the lesson made visible.
- **Follow-ups:** "Why `loguru` over `structlog`?" / "Would you propagate a request_id across the multi-script `06-full-etl/` flow?" / "Where do these logs go — stdout, file, CloudWatch?"
- **Weak answer:** "Add logging" without picking a specific shape or a what-to-measure list.

### Q2.4 — What's your second curriculum thread if you wanted to extend the project beyond batch?

## Round 3 — Alternatives considered (the "why not X?" round)

### Q3.1 — Why not PySpark + Delta Lake instead of Polars + deltalake?

- **Model answer:** PySpark wins when data exceeds single-machine RAM (~100 GB+ working set) or when you need distributed shuffles. The fintech use case here is single-machine batch ETL on GB-scale data inside Lambda — Spark's JVM warmup alone (~30 seconds) and cluster provisioning overhead make it the wrong shape. Polars + deltalake runs in-process, fits the Lambda 15-minute / 10 GB envelope, and uses the same Delta table format (a Spark consumer could read these tables tomorrow). The tradeoff becomes wrong at TB-scale, when joins need cross-machine shuffle, or when a team already runs Spark for other reasons (operational cost of a second stack outweighs the per-job efficiency).
- **Follow-ups:** "How would you know you've crossed the threshold from 'good fit' to 'wrong tool'?" / "If you had to migrate to Spark in two years, what part of this codebase would survive untouched?"
- **Weak answer:** "Spark is slower" — no operational-cost reasoning.

### Q3.2 — Why merge for upserts instead of just full-table overwrite each time?

- **Model answer:** Merge only rewrites the Parquet files that contain matched or inserted rows; overwrite rewrites everything. At 200 rows the difference is invisible (see `s01_basic_upsert.py`); at 200 baseline + 50 merge (see `s02_credit_profile.py`) you can inspect S3 and see only 2–3 Parquet files were touched. At realistic scale — 100M-row Silver table with a 10K-row daily upsert — the difference is hours vs minutes. The non-obvious cost of merge is that it requires Delta's transaction log to identify the affected files, so first-time setup overhead exists; that pays back the first time you do a real upsert.
- **Follow-ups:** "When would overwrite be the right call?" (answer: full re-build from canonical source, or table small enough that the merge planning cost dominates) / "What happens if the merge source has duplicate keys?"
- **Weak answer:** "Merge is more efficient" — no scale numbers, no acknowledgment of merge's planning cost.

### Q3.3 — Why use `s3pathlib` for path manipulation instead of raw boto3 string templating?

- **Model answer:** `s3pathlib.S3Path` lets you chain operations like `s3dir_root.joinpath("bronze").to_dir()` — pathlib-style ergonomics for S3 URIs. Raw boto3 means `f"s3://{bucket}/{prefix}/bronze/"` string templating, which is where trailing-slash bugs and empty-path-segment bugs live. The methods like `.delete(bsm=bsm)` and `.iterdir(bsm=bsm)` work directly on path objects, so you don't need to remember boto3's `list_objects_v2` pagination contract every time. The cost is one more dependency to learn; the gain is removing a whole class of stringly-typed S3 bugs that show up only at runtime.
- **Follow-ups:** "What's `s3pathlib`'s overhead vs raw boto3 on a 10K-object list?" / "Can `s3pathlib` do everything boto3 can?"
- **Weak answer:** "It's cleaner" — no concrete bug class named.

### Q3.4 — Why mixin composition for `one` instead of dependency injection?

- **Model answer:** Mixins keep the wiring centralized — every consumer just imports `one` and gets all capabilities. DI would push the wiring onto 16 example scripts, each constructing their own `boto_ses + s3 + config` triplet. That's a lot more boilerplate per script, and the "single source of truth" property is lost. The mixin tradeoff is MRO complexity — debugging "where does `one.s3_bucket` come from?" requires understanding Python's method resolution order. For a teaching repo where consumers outnumber capabilities, mixins are the right call; for a library shipped to many teams who want to swap implementations, DI would be better.
- **Follow-ups:** "How would you test a mixin in isolation?" / "If you wanted to swap `OneS3Mixin` for a `OneGCSMixin`, how would you do it without touching the example scripts?"
- **Weak answer:** "Mixins are cleaner" — no acknowledgment of MRO cost or comparison with DI.

## Round 4 — Problems hit / how solved (or hypothetical debugging)

### Q4.1 — You re-run `s02_append.py` three times and the Silver table has duplicated rows. Walk me through how you'd debug.

- **Model answer:** First confirm append is the right blame: `s02_append.py` writes to its own table prefix, not Silver, so the duplicates probably aren't from this script. Then check `s02_silver_etl.py`'s `unique(subset=["transaction_id"])` — that's the dedup gate. If duplicates survived dedup, either (a) the subset is wrong (e.g., `transaction_id` is NULL in some rows and `unique` keeps all NULL-keyed rows by default in some configurations), or (b) ETL is run multiple times *with overwrite* and each run captures only one batch. Use `DeltaTable(silver_uri).history()` to see the commit log — that tells you how many writes landed and what their `operationParameters` were. If the commit log shows multiple overwrite commits with shrinking row counts, the bug is "we re-ran ETL without re-reading the latest Bronze". If the commit log shows merge commits and duplicates still appear, the merge predicate is the suspect.
- **Follow-ups:** "What's the first thing you'd actually type at a terminal?" / "How would you tell merge-source duplicates apart from merge-target duplicates?"
- **Weak answer:** "Check the dedup step" — no use of `history()`, no hypothesis tree.

### Q4.2 — A second engineer runs `vacuum` on Silver in production while another reader has a long-running query against an older version. What happens, and how do you prevent it?

- **Model answer:** The reader's query will fail mid-read with `FileNotFoundError` once it tries to fetch a Parquet that vacuum just deleted. There's no "graceful" failure — the read is destructive. Prevention has three layers: (1) Don't use `vacuum(retention_hours=0, enforce_retention_duration=False)` outside of `examples/05-vacuum-schema/s01_vacuum.py` — that script is demo-only. (2) Use the default 168-hour retention (or longer than your longest expected query) so concurrent readers always have a safe window. (3) Coordinate vacuum windows with a runbook — vacuum is operational maintenance, not a routine job.
- **Follow-ups:** "What if a long-running query is supposed to take 8 hours and you vacuum at the 7-hour mark?" / "Is there a way to make readers fail fast instead of mid-read?"
- **Weak answer:** "Use a longer retention" — no description of the failure mode.

### Q4.3 — Schema evolution: you added a column via `schema_mode="merge"` last month. A new ingest fails because the upstream schema dropped a column. Walk through what happens.

- **Model answer:** If the upstream DataFrame is missing a column that the table already has, `schema_mode="merge"` doesn't help — that flag adds columns, doesn't tolerate removed ones. The write either fails with a schema mismatch error, or (depending on deltalake's exact behavior in this version) succeeds by writing NULL for the missing column. Walk through: re-run with `.write_delta(..., schema_mode="overwrite")` if you want to wipe the old schema and replace, or add the dropped column back into the DataFrame as a NULL before writing if you want to preserve historical data. Long-term, schema contracts (pydantic / pandera) at the ingest boundary catch this before it reaches the table.
- **Follow-ups:** "What's the difference between `schema_mode="merge"` and `schema_mode="overwrite"`?" / "How would you handle a type change (e.g., int → float) on an existing column?"
- **Weak answer:** "Just use `schema_mode="merge"`" — doesn't address the dropped-column direction.

## Round 5 — Production pushbacks (senior pressure)

### Q5.1 — Your Bronze ingest is currently 10K rows/batch. Your boss tells you tomorrow it's 100M rows/batch. What breaks first?

- **Model answer:** Three things break in order. (1) `pl.read_ndjson("file.json")` loads the whole file into RAM — 100M rows of JSON is ~50–100 GB depending on schema width, well past a Lambda's 10 GB ceiling. You'd need streaming reads or partitioned input files. (2) `.unique(subset=["transaction_id"])` on a 100M-row DataFrame is doable in Polars (~tens of GB RAM, single-machine) but you've left Lambda territory. (3) The `.map_elements` SHA-256 step in `s02_silver_etl.py` becomes the wall-clock bottleneck — calling Python row-by-row at 100M scale is hours. Mitigations: switch to lazy mode (`pl.scan_ndjson`), partition the input by date/hour, replace `map_elements` with a batched UDF or pre-hash upstream. At this scale you're on the boundary where PySpark starts winning operationally.
- **Follow-ups:** "Could you split the merge into 10x10M-row chunks?" / "Where would Polars vs Spark cross over for you here?"
- **Weak answer:** "Polars handles it" — no breakdown of which specific step fails.

### Q5.2 — Your Silver table just got corrupted — a merge wrote rows that aren't there in the source. Walk me through the incident response.

- **Model answer:** Stop writes first. Then `DeltaTable(silver_uri).history()` to identify the bad commit's version number. Use time travel to read Silver at version `bad - 1` (`pl.read_delta(silver_uri, version=bad-1, ...)`) and verify it's clean. Quick mitigation: write that clean version back as a fresh `mode="overwrite"` so all current readers see the good state. Then root-cause: look at the merge's `operationParameters` in the history (predicate, source row count, matched count) — if matched + inserted ≠ source rows, the predicate is wrong. If that's clean, suspect upstream: was the source DataFrame correct, or was it computed wrong? Postmortem the predicate logic and add a row-count assertion to the merge wrapper for next time.
- **Follow-ups:** "Why not just delete the bad commit JSON?" (answer: doesn't roll back the Parquet writes, and downstream readers may have already read the bad data) / "How would you backfill if the bad commit was 3 weeks ago and you've vacuumed since?"
- **Weak answer:** "Restore from time travel" — no step-by-step incident response.

### Q5.3 — `deltalake` releases v2.0 next month with breaking API changes. How do you know whether to upgrade?

- **Model answer:** First, the version pin in `pyproject.toml` (`deltalake>=1.5.1,<1.6.0`) means `uv sync` won't auto-upgrade — explicit decision required. To evaluate v2.0: (a) read the changelog to identify which APIs the example scripts use have changed (likely `merge`, `vacuum`, `history`). (b) Spin up a branch with the new pin, run the full example suite, see what breaks. (c) The hard part is forward-compat for the on-disk format — confirm v2.0 can read tables written by v1.5 and vice versa during the transition window. If yes, upgrade is mechanical; if not, you need a one-shot rewrite plan. Given there are zero tests, the rebuild-and-eyeball step is the only verification today — which is precisely why test depth is the top elevation item.
- **Follow-ups:** "What's the rollback story if you upgrade and find a regression a week later?" / "How does the lack of CI affect this decision?"
- **Weak answer:** "Try it and see" — no risk assessment.

### Q5.4 — Why should I, as a hiring manager, believe this project shows production engineering judgment and not just "ran a tutorial"?

- **Model answer:** Three things distinguish it. (1) The architectural choices are *named and defended* — Polars + deltalake instead of Spark because of the Lambda envelope, mixin composition because of file-level testability, `AWS_S3_ALLOW_UNSAFE_RENAME=true` flagged as demo-only with the production safe-version explicitly mapped out. (2) The curriculum has internal structure — `02-polars-etl/` deliberately separated from S3, `s02_append.py` deliberately running twice to surface the dedup gap, `batch_1.json` deliberately containing a duplicate. None of those are accidents. (3) The elevation roadmap (`03-elevation-roadmap.md`) names what's missing in the same voice — test depth, CI, the demo-vs-prod boundary — which is the engineering judgment that the work itself is honest about its own limits. If those three don't convince you, that's fair feedback and I'd want to know what would.
- **Follow-ups:** "What would a worse version of this project look like?" / "What's the one thing you'd want to push back on in your own pitch?"
- **Weak answer:** Defensive ("I really did build it"). The right move is to point at concrete evidence inside the project.
