# 05 — Interview Playbook

## Opening — the 90-second pitch

**Model script (~150 words):**

> I built this project while working on a data modernization initiative at a financial org. The production system needed incremental upserts, schema evolution, and time travel for audit — all on S3 without Spark.
>
> To sharpen my understanding, I extracted the core patterns into a collection of 16 POC scripts, organized as 7 progressive modules. Each isolates a single concept: basic Delta Lake I/O, Polars ETL transformations, merge/upsert, time travel, vacuum, schema evolution — and they culminate in a full Bronze-to-Silver incremental ETL pipeline.
>
> The stack is Polars for data processing and delta-rs (the Rust Delta Lake implementation) for table management on S3. No Spark, no JVM — just Python calling Rust libraries. The scripts are idempotent and use mock data, so anyone can run them from scratch.
>
> The most interesting part is the full ETL module — it demonstrates an end-to-end pipeline with PII masking, dedup, incremental merge, and time-travel verification.

## Round 1 — What you have

### Q1.1: Walk me through the data flow in the full ETL pipeline (module 06).

**Model answer:** Raw JSON records land in `batch_1.json` (10 transactions). `s01_bronze_write.py` reads them with `pl.read_ndjson()` and writes to a Bronze Delta table on S3 — raw, no transformations. `s02_silver_etl.py` reads all of Bronze, deduplicates on `transaction_id`, SHA-256 hashes `card_id` for PII masking, filters out DECLINED transactions, and adds an `etl_ts` timestamp. The result (7 rows from 10) writes to Silver. `s03_incremental.py` appends a second batch (5 rows, 2 overlapping) to Bronze, re-runs the full ETL, then merges into Silver using `transaction_id` as the key — updating 2 existing rows and inserting 3 new ones. Time travel comparison between Silver v0 and v1 verifies the merge.

### Q1.2: How do Polars and deltalake (delta-rs) interact? What does each own?

**Model answer:** Polars owns all in-memory data processing — DataFrame creation, transformations (filter, join, dedup, hash), and I/O (`read_delta`, `write_delta`, `read_ndjson`). deltalake (delta-rs) owns the Delta Lake protocol — transaction log management, merge operations (`DeltaTable.merge()`), vacuum, history/versioning. The handoff point is `write_delta` and `read_delta` (Polars) vs. `DeltaTable()` (deltalake). Both need S3 credentials via `storage_options`. The merge API is on `DeltaTable`, not Polars — you construct a `DeltaTable` reference, call `.merge(source=polars_df, ...)`, configure match/no-match actions, then `.execute()`.

**Follow-ups:**
- "Could you replace Polars with Pandas? What would you lose?"
- "What Rust boundary are you crossing when you call `df.write_delta()`?"

**Weak answer sounds like:** Conflates the two libraries or thinks PySpark is involved.

### Q1.3: Explain the `one` singleton pattern. Why is it designed this way?

### Q1.4: What makes each example script idempotent, and why does that matter?

**Model answer:** Every script starts by calling `s3dir_example.delete(bsm=bsm)` to delete the entire S3 directory, then rebuilds from scratch. This means you can run any script N times and always get the same result. It matters for learning (safe to experiment) and for CI (scripts don't leave state that affects other runs). The pattern mirrors production idempotent ETL — you want pipelines that produce the same output regardless of how many times they run.

**Follow-ups:**

### Q1.5: Walk me through the three Delta write modes and when you'd use each in production.

**Model answer:** `overwrite` replaces all data — use for dimension tables or full snapshots where you always want the latest. `append` adds rows without dedup — use for event logs or Bronze layer where you want complete history. `error` fails if the table exists — use as a safety guard for one-time loads or when you want to prevent accidental data clobbering. The key gotcha: `append` does NOT deduplicate, so if you need upsert semantics, you must use `DeltaTable.merge()` instead.

**Follow-ups:**
- "What if you need overwrite semantics but also need to preserve history?"
- "How does overwrite interact with Delta's transaction log?"

**Weak answer sounds like:** Knows the modes exist but can't articulate when to use each.

### Q2.2: The project uses `AWS_S3_ALLOW_UNSAFE_RENAME=true`. What would you change for production?

**Model answer:** I'd switch to DynamoDB-based locking (`AWS_S3_LOCKING_PROVIDER=dynamodb`) or use S3's newer conditional write feature (`If-None-Match`). The unsafe rename skips commit-level locking — fine for single-writer POC but would cause lost updates or corrupt transaction logs with concurrent writers. I'd provision a DynamoDB lock table, add the IAM permissions, and configure delta-rs to use it. The tradeoff: adds infrastructure complexity but guarantees ACID semantics.

**Follow-ups:**

## Round 3 — Alternatives considered

### Q3.1: Why Polars over Pandas? When would Pandas be the better choice?

**Model answer:** Polars is Rust-based, lazy-evaluable, and significantly faster for columnar ETL — especially with large datasets. Its expression API (`.with_columns()`, `.filter()`) composes better than Pandas' index-based approach. However, Pandas has a much larger ecosystem (scikit-learn, plotting libraries expect Pandas DataFrames), better documentation, and wider community knowledge. For this project, Polars is the right choice because the workload is pure ETL with no ML or visualization. If I needed to feed into scikit-learn or matplotlib, I might use Pandas or convert at the boundary.

**Follow-ups:**
- "What about DuckDB — could it replace Polars here?"
- "Polars pins to a minor version in this project. Why is that risky?"

**Weak answer sounds like:** Just says "Polars is faster" without understanding the tradeoff space.

### Q3.2: Why delta-rs instead of PySpark's Delta Lake?

**Model answer:** delta-rs is the Rust implementation with Python bindings — no JVM, no Spark cluster. The production system needed Delta features (merge, time travel, schema evolution) but ran in lightweight containers, not a Spark cluster. PySpark Delta Lake requires a Spark context, which adds 10-30 seconds startup time and significant memory overhead. For single-machine ETL or Lambda/container workloads, delta-rs is the right choice. The tradeoff: PySpark has a larger feature set (Z-ordering, OPTIMIZE, better large-scale shuffle) and a bigger community.

**Follow-ups:**
- "What Delta Lake features are missing from delta-rs?"
- "At what data scale would you switch to PySpark?"

**Weak answer sounds like:** Doesn't know that delta-rs and PySpark's Delta Lake are different implementations.

### Q3.3: Why S3 for storage? What are the alternatives?

**Model answer:** S3 is the de facto standard for data lakes — cheap, durable (11 nines), infinitely scalable. The financial org's production system was already on AWS. Alternatives: Azure ADLS (if on Azure), GCS (if on GCP), MinIO (self-hosted S3-compatible). For Delta Lake specifically, S3 has a known gap: no atomic rename, which is why the project needs the unsafe-rename flag or DynamoDB locking. ADLS and GCS have atomic rename natively, making Delta Lake simpler to operate.

## Round 4 — Problems hit

### Q4.1: What's the trickiest debugging scenario with Delta tables on S3?

**Model answer:** Schema mismatches when writing to an existing table. If you create a DataFrame with a slightly different column order or type (e.g., Int32 vs Int64), the write fails with an opaque error. The fix: always check `DeltaTable(uri).schema()` before writing, or use `schema_mode="merge"` explicitly. Another tricky issue: stale credentials. `polars_storage_options` captures STS temporary credentials at call time — if the session expires mid-pipeline, writes fail with generic S3 errors.

## Round 5 — Production pushbacks

### Q5.1: What if the data volume goes from 10 rows to 10 million rows? What breaks?

**Model answer:** The full-recompute Silver ETL (re-read all of Bronze) becomes the bottleneck — O(10M) per run instead of O(new_batch). The `map_elements()` PII masking would be slow (Python UDF, not Rust-native). Vacuum with `retention_hours=0` would delete files that concurrent readers need. The single-writer pattern holds but would need partitioning (`partition_by="date"`) for query performance. I'd switch to CDC, replace `map_elements` with Polars' native string hashing if available, partition by date, and set vacuum retention to 168+ hours.

### Q5.2: A P0 fires: Silver table has incorrect data. Walk me through your response.

**Model answer:** Step 1: Use time travel to read the last known-good version of Silver (`pl.read_delta(uri, version=N-1)`). Step 2: Identify the bad version by comparing consecutive versions. Step 3: Check `DeltaTable.history()` to find when and what operation produced the bad data. Step 4: If the issue is in the merge source, fix the ETL logic and reprocess from Bronze (Bronze is the source of truth). Step 5: If needed, restore Silver to the last good version using Delta's restore command or by overwriting with the historical version. Step 6: Add a data quality check for the failure mode to prevent recurrence.

### Q5.4: What if AWS temporarily suspended your S3 access during an ETL run?

**Model answer:** Delta Lake's atomic commit protocol protects against partial writes — if the `_delta_log` commit file can't be written, the entire transaction fails and the table stays at the last good version. For the merge in `s03_incremental.py`, either the merge succeeds (new version created) or it doesn't (no change). The idempotent design means I can safely retry. The real risk is a partial write where data files upload but the log commit fails — delta-rs handles this by writing data files first, then the log. Orphaned data files are cleaned up by vacuum later.

**Follow-ups:**
- "What about network partitions — can you get a split-brain scenario?"

**Weak answer sounds like:** Thinks partial data corruption is possible without understanding the commit protocol.
