# 01 — Knowhow Inventory

## Project at a glance

**delta_lake_and_polars_basic** is a hands-on learning repository for Delta Lake and Polars on S3 — without Spark. It was extracted from a real data modernization initiative at a financial organization whose production system supports incremental upserts, schema evolution, and audit-friendly time travel.

The repo contains 16 self-contained proof-of-concept scripts across 7 progressive modules (`examples/00` through `examples/06`). Each script isolates a single concept — reading/writing Delta tables, Polars transformations, merge/upsert, vacuum, schema evolution — and can be run independently with mock data.

A thin core Python package (`delta_lake_and_polars_basic/`) provides AWS credential management and S3 path helpers so every example script shares one consistent configuration.

The architecture is flat: every example script imports the `one` singleton from the core package, then uses Polars and deltalake directly against S3. There is no server, no API layer, no database — just scripts writing/reading Delta tables on S3.

## Component inventory

### 1. Core package — `delta_lake_and_polars_basic/`

#### 1.1 `one` singleton — `delta_lake_and_polars_basic/one/`

- **What:** A configuration singleton assembled via mixin composition that provides AWS credentials, S3 paths, and Polars storage options to all example scripts.
- **Why:** Centralizes AWS configuration so every script uses the same profile, region, bucket, and credential injection pattern. Without it, each of the 16 scripts would duplicate 20+ lines of boto3/s3pathlib setup.
- **Key files:**
  - `delta_lake_and_polars_basic/one/one_01_main.py` — `One` class definition (mixin composition); exports `one` singleton instance.
  - `delta_lake_and_polars_basic/one/one_02_config.py` — `OneConfigMixin`: placeholder `config` property (returns `None`).
  - `delta_lake_and_polars_basic/one/one_03_boto_ses.py` — `OneBotoSesMixin`: creates `BotoSesManager` from `AWS_PROFILE` env var; provides `bsm`, `boto_ses`, `s3_client`, and `polars_storage_options` (dict with AWS keys for Polars/deltalake S3 access).
  - `delta_lake_and_polars_basic/one/one_04_s3.py` — `OneS3Mixin`: provides `s3_bucket` (from env) and `s3dir_root` (S3Path to the project's root prefix on S3).
  - `delta_lake_and_polars_basic/one/api.py` — Public API: `from .one_01_main import one`.
- **Depends on:** `boto3`, `boto-session-manager`, `s3pathlib`, environment variables (`AWS_PROFILE`, S3 bucket config).
- **Gotchas:**
  - `polars_storage_options` extracts temporary STS credentials at call time. If the session expires, you must re-instantiate or refresh.
  - `AWS_S3_ALLOW_UNSAFE_RENAME` is set to `"true"` — this skips DynamoDB-based locking. Fine for single-writer POC; dangerous in multi-writer production.

#### 1.2 Path management — `delta_lake_and_polars_basic/paths.py`

- **What:** `PathEnum` class providing absolute filesystem paths to project directories (project root, examples dir, etc.).
- **Why:** Avoids hardcoded relative paths in test helpers and scripts.
- **Key files:** `delta_lake_and_polars_basic/paths.py`
- **Depends on:** Python `pathlib`.

#### 1.3 Test infrastructure — `delta_lake_and_polars_basic/vendor/pytest_cov_helper.py`

- **What:** Helper functions `run_unit_test()` and `run_cov_test()` that invoke pytest as a subprocess with coverage flags.
- **Why:** Enables the `if __name__ == "__main__":` testing pattern — each module's test file can be run standalone and produce a coverage report.
- **Key files:**
  - `delta_lake_and_polars_basic/vendor/pytest_cov_helper.py`
  - `delta_lake_and_polars_basic/tests/helper.py` — re-exports the above.
- **Depends on:** `pytest`, `pytest-cov`, `subprocess`.

### 2. Examples — `examples/`

All examples follow a shared design pattern:

- **Idempotent startup:** Each script deletes and recreates its own S3 directory at the top, so it can be rerun indefinitely.
- **Mock data:** Either inline `pl.DataFrame({...})` or small JSON files under `data/`. No real data, no external data sources.
- **Single import:** `from delta_lake_and_polars_basic.one.api import one` for AWS config.
- **Self-verifying:** Scripts print results and/or assert correctness (especially in 03 and 06).

#### 2.1 `examples/00-minimal-poc/` — Golden reference

- **What:** A single script (`s01_minimal_poc.py`) that demonstrates the complete read-write-merge cycle in ~70 lines. This is the authoritative example for coding conventions.
- **Why:** Provides a minimal, copy-pasteable template for "Polars + Delta Lake + S3 round-trip with upsert." Every other example builds on patterns established here.
- **Key files:**
  - `examples/00-minimal-poc/s01_minimal_poc.py` — Create 2-row DataFrame, write to S3 Delta, read back, upsert 2 rows (update 1 + insert 1), verify final state.
  - `examples/00-minimal-poc/README.md` — 418-line background primer on S3, Polars, and Delta Lake from first principles.
- **Depends on:** `polars`, `deltalake.DeltaTable`, `one` singleton.
- **Gotchas:** The README here is teaching material, not production documentation.

#### 2.2 `examples/01-delta-read-write/` — Basic Delta Lake I/O

- **What:** Three scripts demonstrating the three Delta write modes: `overwrite`, `append`, and `error`.
- **Why:** These modes have fundamentally different semantics (replace-all vs. add-rows vs. fail-if-exists) and choosing the wrong one in production causes data loss or duplication.
- **Key files:**
  - `s01_overwrite.py` — Write 5 rows with `mode="overwrite"`, read back, verify.
  - `s02_append.py` — Write 3 rows, append 2 more (including duplicate id). Shows append does NOT deduplicate.
  - `s03_error_mode.py` — Write once succeeds, second write raises `DeltaError`. Demonstrates atomic failure.
- **Depends on:** `polars` (write_delta, read_delta), `one` singleton.
- **Gotchas:** Append mode silently adds duplicates — this trips up beginners who expect upsert behavior.

#### 2.3 `examples/02-polars-etl/` — Core Polars data processing

- **What:** Three scripts covering core Polars DataFrame operations — all in-memory, no S3.
- **Why:** Polars is the ETL engine for this project. These scripts build fluency in its API before combining it with Delta Lake.
- **Key files:**
  - `s01_column_ops.py` — `with_columns`, `drop`, `cast`, `filter`, `select` on a 5-row transactions dataset.
  - `s02_dedup_agg.py` — `unique`, `group_by().agg()`, `join` (inner/left/full outer) on orders + customer reference table.
  - `s03_transform.py` — `map_elements` (custom function per row), `when/then/otherwise` (conditional), SHA-256 PII masking, chained transforms.
- **Depends on:** `polars` only. No S3, no Delta Lake.
- **Gotchas:** `s03_transform.py` introduces the SHA-256 PII masking pattern reused in `06-full-etl`.

#### 2.4 `examples/03-merge-upsert/` — Delta Lake merge / upsert

- **What:** Two scripts demonstrating Delta Lake's merge operation at different scales.
- **Why:** Merge/upsert is the critical production operation — it atomically updates existing rows and inserts new ones. The financial use case depends on it for incremental data loads.
- **Key files:**
  - `s01_basic_upsert.py` — 2-row initial, 2-row upsert source. Minimal merge: `when_matched_update_all()` + `when_not_matched_insert_all()`.
  - `s02_credit_profile.py` — 200-row baseline, 50-row merge source (30 updates + 20 inserts). Includes verification assertions (row count, specific field updates, untouched rows).
- **Depends on:** `polars`, `deltalake.DeltaTable`, `one` singleton.
- **Gotchas:** The merge predicate string (`"target.id = source.id"`) uses SQL-like syntax with aliases — easy to get wrong.

#### 2.5 `examples/04-time-travel/` — Version-based historical reads

- **What:** Two scripts demonstrating Delta Lake's versioned reads and commit history inspection.
- **Why:** Time travel is a core Delta Lake feature for audit trails and debugging — every write creates a new version, and any historical version can be read back.
- **Key files:**
  - `s01_version_read.py` — Write 3 versions (different row counts), read each by version number: `pl.read_delta(uri, version=N)`.
  - `s02_history.py` — Create multiple versions, call `DeltaTable.history()` to inspect commit log (version, timestamp, operation). Also `DeltaTable.version()` and `.file_uris()`.
- **Depends on:** `polars`, `deltalake.DeltaTable`, `one` singleton.
- **Gotchas:** `version=0` is the first write, not an empty table.

#### 2.6 `examples/05-vacuum-schema/` — Maintenance operations

- **What:** Two scripts for table maintenance: vacuum (storage cleanup) and schema evolution (add columns).
- **Why:** Production Delta tables accumulate orphaned Parquet files and evolve their schema over time. Both operations are critical for long-lived tables.
- **Key files:**
  - `s01_vacuum.py` — Write 4 versions, list S3 objects, vacuum with `retention_hours=0` (demo only — production uses 168+), verify old files removed.
  - `s02_schema_evolution.py` — Write 3 rows with schema (id, name), then append 2 rows with (id, name, email) using `schema_mode="merge"`. Old rows get `email=null`.
- **Depends on:** `polars`, `deltalake.DeltaTable`, `s3pathlib`, `one` singleton.
- **Gotchas:** `retention_hours=0` with `enforce_retention_duration=False` is unsafe in production — it deletes ALL old files including those needed for concurrent reads.

#### 2.7 `examples/06-full-etl/` — End-to-end Bronze-to-Silver pipeline

- **What:** Three sequential scripts implementing a complete incremental ETL pipeline with Bronze (raw) and Silver (cleaned) layers.
- **Why:** This ties together all previous concepts (read/write, transforms, merge, time travel) into a realistic data pipeline pattern. It mirrors the production system this project was extracted from.
- **Key files:**
  - `s01_bronze_write.py` — Read `data/batch_1.json` (10 NDJSON transaction records), write to Bronze Delta table.
  - `s02_silver_etl.py` — Read Bronze, apply ETL: dedup on `transaction_id`, SHA-256 mask `card_id` (PII), filter out `DECLINED`, add `etl_ts`. Write 7-row Silver table.
  - `s03_incremental.py` — Append `data/batch_2.json` (5 rows, 2 overlapping) to Bronze. Re-run ETL. Merge into Silver. Verify with assertions and time travel comparison.
  - `data/batch_1.json` — 10-row mock transaction batch.
  - `data/batch_2.json` — 5-row incremental batch (3 new + 2 updates).
- **Depends on:** `polars`, `deltalake.DeltaTable`, `one` singleton, `hashlib`.
- **Gotchas:**
  - Scripts MUST run in order: `s01 -> s02 -> s03`.
  - The Silver ETL re-reads full Bronze each time — this is a "recompute Silver" pattern, not a true CDC (change data capture) approach.

### 3. Configuration files

#### 3.1 `pyproject.toml`

- **What:** Python package metadata, dependency declarations, and build config.
- **Why:** Defines the installable package and pins dependency version ranges.
- **Key dependencies:** `deltalake>=1.5.1,<1.6.0`, `polars>=1.39.3,<1.40.0`, `boto3>=1.42.95`, `boto-session-manager>=1.8.1`, `s3pathlib>=2.3.6`.
- **Gotchas:** Version pins are tight (minor-version locked for polars and deltalake) to ensure reproducibility.

#### 3.2 `mise.toml`

- **What:** Task runner and tool version management.
- **Why:** Provides a consistent dev environment (Python 3.12, uv, claude) and one-command workflows (`mise run inst`, `mise run cov`).
- **Key tasks:** `inst` (install deps), `test` (pytest), `cov` (coverage), `build-doc` (Sphinx), `build` (wheel), `publish` (PyPI).

#### 3.3 `.env` / `.env.example`

- **What:** AWS profile configuration (`AWS_PROFILE`, S3 bucket name).
- **Why:** The `one` singleton reads these to initialize the boto3 session and S3 paths.
- **Gotchas:** `.env` is gitignored. `.env.example` shows the expected variables.

## Conventions

1. **Script naming:** `sNN_descriptive_name.py` — sequential within each module.
2. **Idempotent pattern:** Every example starts with `s3dir.delete()` then rebuilds. Safe to rerun.
3. **Import convention:** `from delta_lake_and_polars_basic.one.api import one` at the top; extract `bsm` and `storage_options` as local variables.
4. **Print-heavy style:** Scripts print intermediate DataFrames with `rich` or plain `print()` for visual verification.
5. **No classes in examples:** All scripts are procedural/functional — top-level statements with occasional helper functions.
6. **Mixin composition for `One`:** The singleton is built from mixins (`OneConfigMixin`, `OneBotoSesMixin`, `OneS3Mixin`) rather than a monolithic class. Each mixin owns one concern.
