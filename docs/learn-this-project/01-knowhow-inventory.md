# 01 — Knowhow Inventory

## Project at a glance

**delta_lake_and_polars_basic** is a hands-on learning repository for **Delta Lake + Polars on S3 — without Spark**. It was extracted from a real data-modernization initiative at a financial organization whose production data lake supports incremental upserts, schema evolution, and audit-friendly time travel.

The repo contains **16 self-contained proof-of-concept scripts** across **7 progressive modules** (`examples/00-minimal-poc` through `examples/06-full-etl`). Each script isolates a single concept — reading/writing Delta tables, Polars transformations, merge/upsert, time travel, vacuum, schema evolution, and a full Bronze→Silver pipeline — and is runnable independently with mock data.

A thin core package (`delta_lake_and_polars_basic/`) provides AWS credential management, an S3 path root, and Polars-compatible storage options. All 16 example scripts share that one singleton (`one`) so a learner configures AWS once and never re-types boto3 boilerplate.

The architecture is intentionally **flat**: no server, no API layer, no database. Every example script imports the `one` singleton, derives an S3 sub-path from `one.s3dir_root`, and uses `polars` + `deltalake` directly against S3. Everything is in-process and Lambda-shaped.

## Component inventory

### 1. Core package — `delta_lake_and_polars_basic/`

#### 1.1 `one` singleton — `delta_lake_and_polars_basic/one/`

- **What:** A single instance (`one = One()`) assembled via **mixin composition** that exposes AWS session, S3 client, an S3 root path, and a `polars_storage_options` dict for every example script.
- **Why:** Centralizes AWS configuration so all 16 scripts use the same profile, region, bucket, and credential injection pattern. Without it, each script would duplicate ~20 lines of boto3 + s3pathlib boilerplate. The mixin shape (instead of a monolithic class) lets future capabilities (e.g., `OneGlueJobMixin`) be added without touching existing files.
- **Composition site:** `one/one_01_main.py` — `class One(OneConfigMixin, OneBotoSesMixin, OneS3Mixin): pass; one = One()`. Public import path: `from delta_lake_and_polars_basic.one.api import one`.
- **Key files:**
  - `one/one_01_main.py` — final class definition + singleton instantiation.
  - `one/one_02_config.py` — `OneConfigMixin` (placeholder for future config loading; currently returns `None`).
  - `one/one_03_boto_ses.py` — `OneBotoSesMixin` (boto3 + `BotoSesManager` + `polars_storage_options` dict).
  - `one/one_04_s3.py` — `OneS3Mixin` (`s3_bucket`, `s3dir_root` derived from account alias).
  - `one/api.py` — single `from .one_01_main import one` re-export so consumers have a stable import path.
- **Depends on:** `boto3`, `boto_session_manager.BotoSesManager`, `s3pathlib.S3Path` + `s3pathlib.context`, `os.environ["AWS_PROFILE"]`.
- **Gotchas:**
  - `polars_storage_options` ships **frozen** credentials (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN) plus `AWS_S3_ALLOW_UNSAFE_RENAME="true"`. The last flag tells `deltalake` it's OK to skip the DynamoDB-based commit lock — fine for a single-writer learning repo, NOT safe for multi-writer production.
  - `s3_bucket` is derived as `{account_alias}-{region}-data`. If your account alias or region differs, the bucket name auto-changes — so a new learner doesn't need to edit code, but does need a bucket matching that pattern (or to override).
  - Module load happens on first import — `one.bsm` triggers a real boto3 session, which fails with `KeyError: 'AWS_PROFILE'` if `.env` isn't loaded.

#### 1.2 `paths.py` — `delta_lake_and_polars_basic/paths.py`

- **What:** A `PathEnum` class whose attributes are `cached_property` instances returning `pathlib.Path` objects for project locations (repo root, package dir, tests dir, etc.). Re-exported as `path_enum`.
- **Why:** Eliminates CWD dependencies. Anywhere in the codebase, `path_enum.dir_project_root` gives the same absolute path regardless of where Python was launched from. Also gives IDE autocomplete on path attributes and makes filesystem layout refactoring a one-place change.
- **Depends on:** `pathlib`, `functools.cached_property`.
- **Depended by:** `tests/helper.py`, indirectly by examples via the path-rooted resources in `06-full-etl/data/`.
- **Gotchas:** Roots derive from `Path(__file__).absolute().parent` — moving `paths.py` to a different package depth would silently break every consumer.

#### 1.3 `tests/helper.py` — `delta_lake_and_polars_basic/tests/helper.py`

- **What:** Project-specific wrapper around `vendor/pytest_cov_helper.py`. Exposes `run_unit_test(script)` and `run_cov_test(script, module, preview=False, is_folder=False)` that bake in `root_dir=path_enum.dir_project_root` and `htmlcov_dir=path_enum.dir_htmlcov`.
- **Why:** Lets each test file invoke `run_cov_test(__file__, "package.module")` without re-passing project paths every time. Pairs with the per-file pytest subprocess pattern (see §1.4).
- **Depends on:** `vendor.pytest_cov_helper`, `paths.path_enum`.
- **Gotchas:** Currently the only file under `tests/` other than `__init__.py` — there are no real test files yet (this is an obvious gap; see `03-elevation-roadmap.md`).

#### 1.4 `vendor/pytest_cov_helper.py` — `delta_lake_and_polars_basic/vendor/pytest_cov_helper.py`

- **What:** Subprocess pytest launcher with **per-module coverage isolation**. `run_unit_test(script, root_dir)` shells out to `pytest -s --tb=native <script>`. `run_cov_test(script, module, root_dir, htmlcov_dir, preview=False, is_folder=False)` shells out to `pytest --cov=<module> --cov-report term-missing --cov-report html:<htmlcov_dir> <script>`.
- **Why:** Standard `pytest-cov` measures the whole project on every run. This helper scopes coverage to one module so you can run a single test file from your IDE and get an isolated HTML report for that module only — fast development feedback. The "subprocess" piece is necessary because pytest carries state inside its own process; launching a fresh subprocess prevents cross-test contamination.
- **Depends on:** `subprocess` (std), nothing else.
- **Depended by:** `tests/helper.py`.
- **Gotchas:** Subprocess pytest is slower than in-process pytest, so this is a **dev-loop convenience tool**, not a CI throughput choice. CI typically uses `mise run cov` (whole-project).

#### 1.5 `api.py` — `delta_lake_and_polars_basic/api.py`

- **What:** Empty placeholder. Just the `# -*- coding: utf-8 -*-` line.
- **Why:** Reserved for a future package-level export surface. Currently consumers import from `one.api` directly.
- **Gotchas:** Misleading filename — there is no API here yet. WHY (best guess; verify with project owner): the author follows a convention where every package has an `api.py`, and this one was reserved early but never filled in.

#### 1.6 `docs/__init__.py` — `delta_lake_and_polars_basic/docs/`

### 2. Examples — `examples/`

#### 2.0 `examples/README.md` — the on-ramp doc

- **What:** Curriculum index. Lists the 7 modules in recommended order, with one-line descriptions of what each demonstrates.
- **Why:** Without this file, a learner staring at `examples/` sees 7 numbered directories and has no idea which to open first. The README defines the intended traversal order and the "why" of each module.

#### 2.1 Module `00-minimal-poc/` — golden reference

- **What:** Single script `s01_minimal_poc.py` that does a complete read-write-merge round-trip in ~80 lines.
- **Why:** Defines coding conventions for every other script: variable naming (`s3dir_` for directories, `s3path_` for files, `df_` for DataFrames), multi-line `.write_delta(...)` call style, cleanup-first idempotency (`s3dir_example.delete(bsm=bsm)` at the top). The verbose 418-line module README explains the broader stack — S3, Parquet, Polars history, Delta Lake architecture, fintech context.
- **APIs touched:** `pl.DataFrame(...)`, `df.write_delta(uri, mode="overwrite", storage_options=...)`, `pl.read_delta(uri, storage_options=...)`, `DeltaTable(uri, storage_options=...).merge(source=df, predicate="...", source_alias="source", target_alias="target").when_matched_update_all().when_not_matched_insert_all().execute()`.
- **S3 touch:** Yes.

#### 2.2 Module `01-delta-read-write/` — the three Delta write modes

- **What:** Three scripts demonstrating Delta Lake's `overwrite`, `append`, and `error` write modes.
- **Why:** Most learners have used Parquet (which only does "overwrite or fail"). Delta's three modes are the first concept that distinguishes a *table format* from a *file format*. Each mode is its own script so the lesson is unambiguous.
- **Scripts:**
  - `s01_overwrite.py` — replace table contents wholesale. Demonstrates the cleanup-first idiom and the read-back-to-verify pattern.
  - `s02_append.py` — add rows without touching existing ones. Deliberately runs append twice to show duplicate rows persist (append does NOT deduplicate — that's the *teaching point* for `03-merge-upsert`).
  - `s03_error_mode.py` — write with `mode="error"` against an existing table; show the `DeltaError` exception and catch it. Demonstrates defensive writes for jobs that should be idempotent.
- **S3 touch:** All three.

#### 2.3 Module `02-polars-etl/` — pure Polars (no Delta, no S3)

- **What:** Three scripts demonstrating the Polars DataFrame API in isolation — no S3, no `read_delta`, no `write_delta`. None of these scripts import `one`.
- **Why:** Pedagogical separation. Learners must build Polars fluency *before* combining it with Delta Lake; otherwise a later bug could be in the Polars half or the Delta half and they can't localize it. This module also doubles as the "no AWS credentials yet? run this first" on-ramp.
- **Scripts:**
  - `s01_column_ops.py` — column-level primitives: `.with_columns(...)`, `.drop(...)`, `.cast(pl.Float64)`, `.filter(pl.col("x") > 0)`, `.select(...)`, `.str.to_uppercase()`.
  - `s02_dedup_agg.py` — `.unique(subset=[...])`, `.group_by(...).agg(pl.count(), pl.col("amount").sum(), .mean())`, `.join(other, on="key", how="left"|"inner"|"outer")`. These are the building blocks for daily-aggregate / customer-profile patterns later.
  - `s03_transform.py` — `.map_elements(lambda v: hashlib.sha256(v.encode()).hexdigest(), return_dtype=pl.Utf8)` for PII masking, and `pl.when(cond).then(x).otherwise(y)` for derived columns. These are the two transforms used by `06-full-etl/s02_silver_etl.py` to build the Silver layer.
- **S3 touch:** None.

#### 2.4 Module `03-merge-upsert/` — the upsert lesson

- **What:** Two scripts demonstrating `DeltaTable.merge(...)`.
- **Why:** Upsert is the single most-asked-for feature in data lakes; pre-Delta you had to do it manually with full-table rewrites. The lesson is "merge predicate + match clauses + execute" pattern.
- **Scripts:**
  - `s01_basic_upsert.py` — minimal 2-row merge. Pure mechanism teaching.
  - `s02_credit_profile.py` — 200-row baseline + 50-row merge in a realistic credit-profile-refresh shape. Same API, but the row counts make the next teaching point land: merge only rewrites *affected* Parquet files, not the whole table.
- **S3 touch:** Both.

#### 2.5 Module `04-time-travel/` — versioned reads

- **What:** Two scripts demonstrating Delta Lake's time-travel and commit-log inspection.
- **Why:** Audit and reproducibility are huge in fintech. Time travel is the answer to "show me what this table looked like at 9am yesterday".
- **Scripts:**
  - `s01_version_read.py` — `pl.read_delta(uri, version=0, ...)`, `... version=1, ...`, then default (latest). Teaches that every Delta write creates an immutable version.
  - `s02_history.py` — `DeltaTable(uri, ...).history()` returns the full commit log (version, timestamp, operation, parameters). Teaches how to answer "who wrote what, when".
- **S3 touch:** Both.

#### 2.6 Module `05-vacuum-schema/` — operational care

- **What:** Two scripts on maintenance.
- **Why:** A real Delta table accumulates old Parquet files forever (kept for time travel). Production needs vacuum to reclaim storage. And schema changes are a recurring nightmare — Delta's `schema_mode="merge"` is the safe path.
- **Scripts:**
  - `s01_vacuum.py` — writes 4 versions, then `DeltaTable(...).vacuum(retention_hours=0, enforce_retention_duration=False)` to delete old files. The `retention_hours=0` + `enforce_retention_duration=False` combination is **demo-only** — production would use 168+ hours (the default) so concurrent readers don't blow up.
  - `s02_schema_evolution.py` — write a wider DataFrame with `.write_delta(uri, schema_mode="merge", ...)`; deltalake automatically nulls old rows for the new column. Lesson: schema migration without a full rewrite.
- **S3 touch:** Both.

#### 2.7 Module `06-full-etl/` — the capstone

- **What:** Three scripts that build a Bronze→Silver pipeline using mock transaction data.
- **Why:** Integration lesson. Everything learned in 01–05 gets composed: ingest (Bronze) → transform (Polars) → write (Silver) → handle a second batch (incremental + merge + time-travel audit).
- **Data:** `data/batch_1.json` (10 NDJSON transactions, one deliberate duplicate `TXN003`) and `data/batch_2.json` (5 incremental rows, 2 overlapping with batch 1 by `transaction_id`). The duplicates are the *teaching point* — dedup must happen in Silver.
- **Scripts (run in order):**
  - `s01_bronze_write.py` — `pl.read_ndjson("data/batch_1.json")` then `.write_delta(uri, mode="overwrite", ...)` into the Bronze table. Lesson: ingest first, transform later.
  - `s02_silver_etl.py` — read Bronze → `.unique(subset=["transaction_id"])` → SHA-256 mask `card_id` → filter out `auth_status == "DECLINED"` → add `etl_ts` → `.write_delta(...)` into Silver. Combines techniques from `02-polars-etl` with Delta I/O.
  - `s03_incremental.py` — append batch 2 to Bronze, re-run ETL on the new data, **merge** into Silver, then use **time travel** to compare Silver v0 vs v1 (the audit step).
- **S3 touch:** All three.

## Conventions

- **Naming inside example scripts:**
  - `s3dir_xxx` — variables holding an S3 directory (`S3Path` with trailing slash).
  - `s3path_xxx` — variables holding an S3 file.
  - `df_xxx` — Polars DataFrames.
  - `delta_uri` — string URI passed to `pl.read_delta` / `pl.DataFrame.write_delta` / `DeltaTable(...)`.
  - All-caps SQL keywords in merge predicates (e.g., `"target.id = source.id"`).
- **Cleanup-first idempotency:** Every script that writes to S3 starts with `s3dir_example.delete(bsm=bsm)`. This is what makes the scripts safe to re-run.
- **Multi-line `.write_delta(...)` call style:** `mode=`, `storage_options=`, and any other kwargs each on their own line. The author treats this as a readability convention because the call is the most-modified piece of every script.
- **Curriculum naming:** `sNN_xxx.py` — the numeric prefix establishes traversal order within a module without requiring an explicit dependency declaration. Same convention is used inside `one/` (`one_01_main.py`, `one_02_config.py`, ...).
- **Mixin composition for the singleton:** Capabilities are added by writing `OneXxxMixin` in a new `one_NN_xxx.py` and adding it to the inheritance list in `one_01_main.py`. Never grow `one_01_main.py` itself.
- **Testing pattern:** Each test file ends with `if __name__ == "__main__": run_cov_test(__file__, "<module>")` so it can be double-clicked from an IDE to run a coverage-scoped pytest subprocess.

## Notable design choices (the "WHY" worth quizzing on)

1. **Singleton + mixin composition.** Why not a monolithic config class? Because each mixin can be tested independently and a new capability (e.g., Glue Catalog integration) becomes a one-file addition.
2. **`sNN_xxx.py` numeric prefix curriculum.** Why not just rely on `examples/README.md` to set the order? Because file-list-sorted-by-name is what the learner sees by default in `ls` and in IDEs — order should be visible without reading prose.
3. **`02-polars-etl/` does NOT touch S3.** Why split it out? So a learner can prove the Polars half works before adding S3/Delta complexity — debug surface area is half.
4. **`AWS_S3_ALLOW_UNSAFE_RENAME="true"` in `polars_storage_options`.** Why? Skips DynamoDB-based commit locking — fine for a single-writer learning repo, NOT safe for multi-writer production. The flag is the explicit "demo mode" tell.
5. **Subprocess pytest for per-module coverage.** Why not just in-process pytest? Because in-process state contaminates between runs; subprocess gives the dev loop a clean run per file.
6. **All scripts start with `s3dir_example.delete(bsm=bsm)`.** Why not check-and-skip? Because the lesson is *idempotency for free* — a learner re-running a script should never have to think about prior state.
7. **`one/api.py` exists but is empty in `delta_lake_and_polars_basic/api.py`.** Why two `api.py` files? Convention: each package level has its own `api.py` as the public-import surface. Only `one/api.py` is filled in — the top-level one is reserved.
